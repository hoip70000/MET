# CLAUDE.md — MET (Manga Editing Tool)

Architecture guide for future Claude sessions working on this repo. Read this before touching `src/components/studio/`.

## What this is

**MET** is a React 19 + TypeScript + Vite + Konva web app for manga/manhwa cleaning, translation, and typesetting. It is a normal bundled SPA (not the single-file/offline architecture described in the orphaned prototype doc at `src/assets/claude.md` — that file documents a *different*, disconnected reference prototype at `src/assets/mangastudio (1).html`; useful as design reference only, not part of the shipping app).

Entry point: `src/App.tsx`, rendered via `src/main.tsx` into `index.html`. Top-level navigation (`src/config/navTabs.ts`) has 5 tabs: Library, Text Editor, Settings, Teams, Cloud — there is still no dedicated Home/landing screen (Recent/Templates/Tutorials/Plugins/Account), see "Known gaps" below.

## Data model

`src/types.ts` defines the persisted hierarchy:

```
Workspace { mangas: MangaSeries[] }
  MangaSeries { volumes: Volume[] }
    Volume { chapters: Chapter[] }
      Chapter { pages: Page[] }
        Page { original: ProcessedImage, cleaned: ProcessedImage | null }
```

`workspaces: Workspace[]` lives in `App.tsx` state, autosaved to IndexedDB (`idb-keyval`, key `workspaces_library`) debounced 800ms (`App.tsx`). Schema evolution goes through `src/lib/migrate.ts`'s `migrateWorkspace()`, run once on load.

Original/cleaned pairing: `src/lib/pages.ts`'s `suggestPairing()` — three passes: exact normalized-filename match, then numeric-page-number match (extracts the trailing digit run from each filename), then positional fallback for whatever's left. Always returns an editable suggestion (`PairingSuggestion`), never a silent final assignment — `PageManager.tsx` surfaces unmatched images as a manual drag-to-pair pool.

## The Studio (`src/components/studio/`)

`Studio.tsx` is the main shell, wrapped in three context providers (`ColorProvider`, `HistoryProvider`, `DockProvider`). Mounted only when a chapter is opened (`App.tsx`, `chapterView === 'studio'`); fully unmounts when navigating back to the page manager or a different chapter, so per-chapter state doesn't need explicit reset logic — a fresh mount is a fresh chapter.

### Per-page layer stack

`layersByPage: Record<pageId, StudioLayer[]>` in `Studio.tsx` — every page always has a locked `Background` layer at **root index 0**. `StudioLayer` (`studioTypes.ts`) covers `background | clean-patch | text | adjustment | group` types, and every one of them is implemented. (A phantom `bubble-mask` member used to sit in this union with no create path and no renderer; it was deleted rather than left as a stub to build against.)

**The stack is a tree, and `src/components/studio/layerTree.ts` owns its invariant** — the same role `textRuns.ts` plays for runs. Groups carry `children`; nothing outside `layerTree` may walk or edit that field by hand, and `updateLayersOnPage` remains the only mutation primitive (every updater handed to it is composed from `layerTree`'s writers). Two rules it enforces: the background is root index 0 always, and `children` exists iff `type === 'group'`. **Illegal operations no-op rather than throw** — cycles, moving the background, reparenting into a non-group. That's deliberate: the Layers panel computes drop intent from mouse geometry, so a bad drag must degrade to nothing happening, never to a corrupted tree. `layerTree.test.ts` covers all of it.

Because every new tree field (`children`, `mask`, `clipped`, `collapsed`) is **optional**, a pre-group (v4) save is already a valid tree — every walker bottoms out immediately on it. That property is what keeps the v5 migration a no-op backfill; don't add a required tree field without rethinking it.

`cloneSubtree` returns an old→new `idMap` and callers **must** feed it to `StudioCanvasHandle.clonePaintCanvases`. The paint/mask registries are keyed by layer id, so duplicating a layer without cloning its canvas hands the copy a blank one — that was a real, silent bug before `layerTree` existed (`handleDuplicateLayer` did `{...source, id: new}` and lost every pixel).

Raster pixel content for `clean-patch` layers lives **only** as live `HTMLCanvasElement`s in `paint/paintCanvasRegistry.ts`, held in a `useRef` inside `StudioCanvas.tsx` — never in React state directly. This registry persists across page switches within a session (keyed by layer id, not page id), which is what lets `StudioCanvas.getExportSnapshot()`/`exportRasterLayers()` capture edits made on any page visited so far, not just the currently active one.

Real, working layer features: opacity, blend mode (`globalCompositeOperation` via `BLEND_TO_COMPOSITE`), visibility, lock, reorder, duplicate, delete. **Layer groups are real** — create/ungroup (Layer menu, `Ctrl+G` / `Ctrl+Shift+G`, or the Layers panel), collapse, reparent by drag-and-drop, group opacity/blend with Photoshop's pass-through-vs-isolated semantics, and they survive PNG and PSD export (ag-psd gets real nested `children`, so a group stays a collapsible folder in Photoshop). **Adjustment layers** (`AdjustmentPanel.tsx`, `src/lib/adjustments.ts`) are real and cover ten types — Brightness/Contrast, Hue/Saturation, Levels, Curves, Exposure, Vibrance, Color Balance, Posterize, Threshold, Gradient Map — and they **affect everything below them in their parent**, honouring their stack position. `layerTree.partitionAdjustments` rewrites each sibling list so every adjustment becomes a wrapper around the layers beneath it (`[A, B, adj1, C, adj2]` → `adj2(adj1(A,B), C)`); the canvas renders each wrapper as a cached Group with `filters()` on it, and `exportImage.ts` walks the same partition — generically, so all ten kinds got live canvas preview and flattened export for free the moment `filterForAdjustment` covered them, no per-kind wiring needed in either renderer. `AdjustmentLayerData` stays one flat interface carrying every kind's fields simultaneously (not a discriminated union), matching how the original three were already shaped. Curves gets a real interactive control-point editor (`CurvesEditor.tsx`, an inline SVG graph — chosen over `<canvas>` because each point needs to be individually hit-testable/draggable, which SVG gives for free) driving a 256-entry LUT via monotonic Catmull-Rom interpolation (`adjustments.ts`'s `curveLut`, exported and sampled directly by the editor's own on-screen curve so the two can never drift — the same "one function, no separate approximation" rule `textLayout.ts`'s `layoutText` already follows); reflecting a duplicated-neighbor point through the near control point rather than reusing it verbatim is load-bearing, not cosmetic — the naive version halves the tangent at both ends and visibly bows a plain 2-point "identity" curve that should render dead straight. Gradient Map is deliberately two-stop only (a `from`/`to` color pair, same shape as `TextGradient`), matching this app's one Gradient tool — no multi-stop gradient editor exists anywhere in this codebase. All ten map onto real `ag-psd` adjustment layer types (verified against the installed `ag-psd` type definitions) for PSD export, so they round-trip as live, editable Photoshop adjustment layers rather than being baked into pixels. **Layer masks are real** — see the dedicated paragraph below. **Not implemented**: smart objects. **Grouping refuses a selection spanning two parents** rather than silently reordering layers the user didn't select (`groupLayers`); the Studio surfaces that as a toast.

**Layer masks are real** (`LayerMask`/`StudioLayer.mask`, `studioTypes.ts`) — any layer type may carry one, groups included, added/removed/enabled-toggled from the Layers panel (a mask thumbnail chip next to the layer's own icon, always visible — click it to make the mask the paint target, click the layer's row to go back) or the Layer menu. Painting is **alpha-only**, not Photoshop's grayscale-luminance model: a brush/tool stroke reveals (raises alpha), the Eraser hides (lowers it), and soft brushes/low flow give feathered partial masks for free by reusing the *entire* existing paint engine unchanged — the same "paint an alpha buffer with real tools" trick Quick Mask already relies on. Adding a mask seeds it from the active selection if one exists (`selectionToAlphaCanvas`, reused verbatim), otherwise fully opaque (reveal-all), matching Photoshop's "Add Layer Mask" default. Mask pixels live in their own registry (`maskCanvasRegistry` — literally the *same* generic functions `paintCanvasRegistry.ts` already exports, reused against a second `useRef`, not a duplicated module) keyed by the mask's own id, mirroring how a layer's own raster pixels are kept separate.

**The mask trim is applied as a Konva `filters()` pass, not a `destination-in` sibling `KonvaImage` inside the cached group** — that was the first implementation, and it went stale: a live-edited mask, once the layer's group was re-cached, could show the *pre-edit* mask forever after, because Konva's shape-level buffer-canvas draw path (`Shape.prototype.drawScene`, used when `_useBufferCanvas()` is true) re-derives a child's own composite operation relative to whichever node is currently being cached — correct for a single cache pass, but not something to blindly re-derive on every keystroke of a paint stroke. A filter sidesteps the question entirely: `maskAlphaFilter(canvas)` reads the mask canvas's *current* pixels fresh on every invocation, and Konva's filter machinery already reruns cheaply (`getImageData -> filter -> putImageData` over the existing cached scene, no full redraw) — the exact mechanism adjustment layers already prove out. An enabled mask forces the same isolation (caching) as an adjustment or a clip run, for the same reason: `filters()` only has something to run against once the node is cached. Editing a masked layer's *own* raster content (not its mask) needed one more fix: `suspendAncestorCaches`/`restoreAncestorCaches` (the "drop a cached ancestor for the duration of a stroke" mechanism that already existed for adjustments/clip-runs) only ever cleared *ancestor* caches, since an ordinary clean-patch layer never caches itself — a masked leaf now does, so painting it needed the target's own cache included, not just its ancestors'.

PSD export converts the alpha-channel mask canvas to grayscale (`r=g=b=alpha`) at the PSD boundary only — `LayerMask`'s own doc comment is explicit that alpha-channel storage is a live-rendering optimization, and ag-psd's `LayerMaskData.canvas` wants Photoshop's grayscale-channel convention instead. PNG/flatten export (`exportImage.ts`) mirrors the live canvas exactly: a masked leaf composites onto a scratch canvas, gets `destination-in`'d by the mask, then blits through the leaf's own opacity/blend — same reasoning as the clip-run scratch-canvas pattern, just for export instead of Konva. `maskRaster` persists alongside `raster` in `SerializedStudioLayer`; both were already-optional v5 tree fields, so wiring masks up needed no schema bump.

Three non-obvious things about adjustments, all of which follow from "the wrapper *contains* the stack it adjusts":

- **Opacity is folded into the filter**, not applied to the wrapper (`adjustments.withStrength` lerps `original → filtered`). Fading the wrapper would fade the *page* to transparent and expose the backing rect, not ease the grade.
- **Hiding is expressed by clearing `filters()`, never by `visible={false}`** on the wrapper — hiding the wrapper blanks everything below it. (It did, briefly; `e2e/adjustments.spec.ts` caught it.)
- **Blend mode is not supported on adjustments and `LayersPanel` hides the control.** Photoshop blends an adjustment's result against its unadjusted backdrop, and the wrapper contains the very stack that backdrop would come from. Unlike opacity it isn't expressible as a per-pixel lerp. An inert dropdown would be worse than none.

**Blend modes were a no-op on screen until the Konva collapse, and nobody noticed** because `exportImage.ts` composites onto a single canvas and applied them correctly the whole time — screen and export silently disagreed. Cause: `Container.drawScene` (`node_modules/konva/lib/Container.js`) applies `globalCompositeOperation` while drawing children **into the current canvas**, and every StudioLayer used to own a separate Konva `Layer`, i.e. a separate canvas that starts empty. Multiply against nothing returns the source. `e2e/compositing.spec.ts` pins this with exact arithmetic (grey×grey must be 64, not 128).

### Canvas engine (`StudioCanvas.tsx`)

**One Konva `Layer` holds the page and its entire stack; each StudioLayer is a `Group`** (`renderLayerNodes`, recursive). Konva `Layer`s are separate canvas elements and cannot nest, so the old layer-per-StudioLayer could express neither groups nor a working blend mode. Consequences worth knowing before editing the render:

- `visible`/`listening` are set from each layer's **own** flags — Konva cascades both down a Group, so a hidden or locked group deafens its whole subtree for free. `layerTree`'s `isEffectivelyVisible/Locked` exist for consumers that *don't* get that free (the exporter).
- `Group` has **no `batchDraw`** (only `Layer` does) — redraws go through `redrawLayerNode`, which hops to `getLayer()`.
- The page backing `Rect` (drop shadow) and the View Original `overlayImage` are **chrome, not content**: they sit outside the layer tree, between the background and the stack. Keep them out of any future group cache.
- **Group isolation is a two-renderer contract.** `needsIsolation` (`StudioCanvas.tsx`) and `isolatesGroup` (`exportImage.ts`) implement the same rule for the canvas and the exporter and **must not drift** — when they did, the screen showed 96 and the file said 128 for the same group. The rule mirrors Photoshop: opacity 1 + normal blend is *pass-through* (children composite against everything below the group, which is what an uncached Konva Group already does for free); anything else is *isolated* (the subtree composites against nothing but itself, then blits once through the group's alpha/blend, via `cache()` / an offscreen canvas). A Multiply child inside an isolated group therefore washes out — correct, and what Photoshop does. **Child count is not a condition**: isolation changes what a child blends *against*, not just how results stack, so "skip the cache for single-child groups" is a real bug, not an optimization. `e2e/export.spec.ts` compares decoded export pixels against a stage sample to hold this.

Konva `Stage` per page. Background image loads into `image` state from `page.original` or `page.cleaned` (via `showCleaned`); when `overlayOpacity > 0` and `showCleaned` is true, `page.original` also loads as a second `overlayImage` rendered on top at that opacity (View Original overlay mode).

Pan: Pan/Select tools drag the Stage natively; **any other tool** pans via Space-hold or middle-mouse-drag, handled manually through `panRef` + window-level `mousemove`/`mouseup` listeners (not Konva's built-in drag, to avoid fighting per-tool pointer handlers).

Tool routing in `handlePaintPointerDown/Move/Up` dispatches by `activeTool` string against several disjoint sets: `MARQUEE_TOOLS` (includes `crop`, which reuses the same rect-drag as Rectangular Marquee), `LASSO_TOOLS` (drag-based freehand only — `lasso-polygon` is click-accumulate, handled separately via `handleStageClick`/`lassoPolyPoints`, mirroring the Pen tool's `penPoints` pattern), `PAINT_TOOLS` (from `paint/usePaintLayer.ts`). Marquee Shift constrains to a perfect square/circle; Shift/Alt held at the start of a marquee/lasso/wand drag instead means add/subtract, see Selection model below.

**Tool-group flyouts** (`toolGroups.ts`'s multi-tool groups — Lasso, Marquee, Healing, Brush, Gradient, etc.): `ToolGroupButton.tsx` renders one rail icon per group plus a small corner triangle when the group has siblings; the sibling picker (`ToolFlyout.tsx`) opens on a long-press (350ms), a click on the triangle, *or* a right-click (which also calls `preventDefault()`, so the browser's own context menu never appears on a tool icon — `AppContextMenu`'s own `defaultPrevented` check is what lets the two systems coexist without conflict). It's positioned via Tailwind classes anchored to the icon (`left-full` = flush right of a vertical rail, `bottom-full` = flush above a horizontal one) — always on that required side, never flipped, even at a narrow viewport. Because that alone doesn't account for the *other* axis, `ToolFlyout.tsx` measures its own rendered `getBoundingClientRect()` in a `useLayoutEffect` and nudges it back on-screen with a `transform: translate(...)` if it would clip past `window.innerHeight`/`innerWidth`, rather than hand-estimating its size from the Tailwind classes (which could silently drift from them). It closes on outside-pointerdown, Escape, picking a tool from it, or — via a `useEffect` in `ToolGroupButton.tsx` keyed on `activeTool` — the moment any tool *outside* this group becomes active (a keyboard shortcut, or picking a different group's own tool), so a stale flyout never lingers open over the canvas.

**New clean-patch layers are seeded with a copy of the background** (`Studio.tsx`'s `handleAddLayer` → `StudioCanvas`'s `seedLayerWithBackground`), not left blank — matches the standard manga-cleaning workflow ("duplicate the scan, clean the duplicate") and is what makes Clone/Heal/Blur/Sharpen/Smudge/Dodge/Burn/Sponge/Content-Aware/Liquify actually useful the moment a layer is created, since those tools only ever read/write the active layer's own canvas, never the (immutable, non-paintable) background underneath it. **This is the layer-initialization contract, not a bug to fix**: a "new layer" in this app has always meant "a working copy of the scan," matching the tools it's paired with — a request to make new layers blank by default would silently break that pairing for every one of those tools. The blank-layer need is real, though, so it's a second, explicit action alongside `handleAddLayer`, not a change to what that one does: `Studio.tsx`'s `handleAddBlankLayer` creates the same kind of `clean-patch` layer but simply never calls `seedLayerWithBackground` — `getOrCreateCanvasFor` already hands back a bare transparent canvas when nothing writes to it, so skipping the seed call is the whole implementation. Reachable via Alt-click on the Layers panel's Add button (`LayersPanel.tsx`, `e.altKey` on the same click handler `onAdd` uses) or Layer > New Blank Layer. Relatedly, **picking any paint-family tool while a non-`clean-patch` layer is active** (e.g. the default Background layer on a freshly opened chapter) **auto-switches to the topmost existing raster layer, or creates one** (`Studio.tsx`, a `useEffect` keyed on `activeTool`) — without this, every brush/fill/shape/liquify tool would silently no-op on first use, since `getActivePaintCanvas()` only returns a canvas for `clean-patch` layers. That scan goes through `layerTree.ts`'s `flattenTree`, not the raw root array, so a raster layer nested inside a group is found and reused instead of triggering a redundant top-level one.

**Magic Wand samples the background composite as a fallback** (`usePaintLayer.ts`'s `getFallbackCanvas`, wired to `StudioCanvas`'s `sampleCanvasRef` — the same hidden canvas the Eyedropper already used) when no clean-patch layer is active, instead of silently operating on a nonexistent/blank raster canvas — otherwise the wand could never select regions of the actual manga art, only whatever happened to be painted on an overlay layer.

**Crop is real** (`StudioCanvas`'s `commitCrop`, triggered by Enter or double-click while the Crop tool is active over a rect selection — mirrors the existing Pen/Polygonal-Lasso "build then Enter/dblclick to commit" convention): trims the background (`page.original` + `page.cleaned`) and every raster layer's canvas to the selection rect, shifts text layers to match, and persists the new page dimensions back up through a new `onPagesChange` prop threaded from `App.tsx`'s existing `handleChapterPagesChange` (previously Studio had no way to mutate page image data at all). Only rectangular selections are supported, matching Photoshop's Crop tool.

**Zoom tool is real**: click zooms in centered on the cursor, Alt-click zooms out — previously selecting it and clicking the canvas did nothing (zoom only ever worked via the scroll wheel or toolbar buttons, regardless of active tool).

All of the above dispatch through **Pointer Events** (`onPointerDown/Move/Up`), not separate mouse/touch handlers — mouse, touch, and pen input share one code path. Real stylus pressure (`PointerEvent.pressure`) scales brush/pencil/eraser size (only for `pointerType === 'pen'`; mouse/touch report a flat, meaningless 0.5 per spec). A `touchCount >= 2` guard skips tool dispatch for pointer events fired mid-two-finger-gesture, deferring to the separate pinch/pan `onTouchMove` handler. Two-finger touch pans *and* pinch-zooms simultaneously (`handleTouchMove` anchors on the *previous* frame's pinch center, not the current one — a plain two-finger drag with no distance change still pans correctly).

Selection model: `paint/selection.ts`'s `Selection` union (`rect | ellipse | polygon | mask`) — vector shapes clip via `Path2D`, magic-wand masks approximate live via bounding box during a stroke and get pixel-perfect refinement on commit (`refineMaskedRegion`, now wired into every paint-stroke commit path, not just magic-wand). **Feather/expand/contract/add-subtract/intersect are real**: Shift(add)/Alt(subtract)/Shift+Alt(intersect) combine the in-progress marquee/lasso/wand shape with the prior selection by rasterizing both to a mask and compositing (`combineSelections`/`combineModeFromModifiers`); a **Select** menu (Deselect, Feather…, Expand…, Contract…, Transform Selection, Make Selection from Path, Quick Mask) applies one-shot pixel-amount ops (`featherSelection`, `growSelection`) via a `swal` numeric prompt. **Magnetic Lasso, Healing Brush, Patch Tool, and Slice are all real** — see Part H tool descriptions elsewhere in this doc (heal/patch share Clone Stamp's alt-click source-point plumbing with color-matched blending; Slice queues rect selections and exports one cropped PNG per rect as a zip; Magnetic Lasso snaps each clicked segment onto nearby strong edges via Dijkstra over a Sobel gradient-magnitude cost field). **A real vector Pen Tool is implemented** — see "Vector paths (Pen Tool)" below.

A marquee/lasso gesture doesn't touch `selection` at all until the pointer clears a small (4 screen px) dead zone (`marqueeDraggedRef`/`lassoDraggedRef`, `StudioCanvas.tsx`) — below that it's an ordinary click (most commonly: starting a paint stroke *inside* an existing selection), not an attempt to draw a new empty one. Below the dead zone, pointerup is a pure no-op: nothing was ever touched, so there's nothing to revert either. Deselecting is otherwise only ever explicit — `Ctrl/Cmd+D`, the Deselect button in the marquee/lasso/wand tool's options bar, or Esc while a plain selection tool (not Crop/Slice, which use Esc for their own draft-cancel) is active with a selection present.

**Selections are per-page.** `Studio.tsx`'s `selection` state is a single flat value, but switching `activePageId` stashes the outgoing page's selection into `selectionByPageRef` (mirroring how `rasterByPageRef`/`maskByPageRef` already keep other per-page data) and restores it if you come back — it's never just reset to none. Quick Mask's scratch alpha canvas (`quickMaskCanvasRef`, a flat non-page-keyed ref inside `StudioCanvas`) and Multi-Bubble/Slice's queued rect arrays (`multiBubbleRects`/`sliceRects`, `Studio.tsx`) are **not** page-scoped the same way — a page switch commits Quick Mask into the outgoing page's stashed selection (same as toggling it off) and clears the queued rects outright, so neither leaks pixels/regions onto whichever page you switch to next.

### Vector paths (Pen Tool)

The Pen and Curvature Pen tools build a real, persisted `path`-type `StudioLayer` (`PathLayerData` — `anchors: PathAnchor[]` with per-anchor `point`/`handleIn`/`handleOut` offsets and a `type: 'corner'|'smooth'` hint, plus `closed`/`fill`/`stroke`/`fillRule`) instead of the old rasterize-and-discard behavior. Anchor placement is a real mousedown/mousemove/mouseup gesture in `StudioCanvas.tsx` (`penDraft`/`penPlacingRef`), not Konva click events: a plain click places a corner anchor, a click-and-drag places a smooth anchor with handles pulled out symmetrically along the drag vector (mirrors Photoshop exactly), and clicking back on the first anchor (with ≥3 already placed) closes the path. Curvature Pen's plain clicks still produce smooth curves without needing a drag — `pathGeometry.ts`'s `applyCurvatureSmoothing` retroactively recomputes the *previous* anchor's handles (a Catmull-Rom-to-bezier tangent) each time a new anchor is appended, since a smooth anchor's handles depend on both neighbors and the anchor just placed doesn't have its next one yet.

**One shared function draws every path anywhere it appears**: `pathGeometry.ts`'s `traceAnchors(ctx, anchors, closed)` does real per-anchor `bezierCurveTo` tracing (genuinely different math from `paintEngine.ts`'s older `tracePenPath`, which is a polyline-smoothing approximation with no independent handle concept, left in place only for anything else still calling it) — against a `Konva.Context` for the live pen preview and `PathLayerNode`'s committed render, or a real `CanvasRenderingContext2D` for export/bake, since both implement compatible `moveTo`/`bezierCurveTo` signatures.

**Path Selection (`path-select`) and Direct Selection (`direct-select`) are both real, and deliberately separate tools** rather than reusing the plain `select` tool — a path has no `x`/`y` (its geometry *is* the anchor list), so dragging it means translating every anchor by the drag delta, a structurally different update than `select`'s "set `x`/`y`" contract. Path Selection's whole-path drag doesn't participate in the Transformer at all (no bounding-box resize, matching real Photoshop) — `PathLayerNode`'s Group resets its own position to `(0,0)` after every drag rather than accumulating a transform, the same principle `TextLayerNode.onTransformEnd` already applies to scale. Direct Selection renders per-anchor/per-handle drag chrome only for the selected path: dragging an anchor moves just its `point` (handles ride along automatically, since they're stored as offsets); dragging a handle patches that one side and mirrors the opposite handle if the anchor is `type: 'smooth'`; **Alt-click an anchor converts it between corner and smooth** (`pathGeometry.ts`'s `toggleAnchorType` — smooth→corner retracts both handles to zero, corner→smooth synthesizes symmetric handles from the anchor's neighbors), matching Photoshop's real gesture (there's no separate Convert Point tool).

**Stroke Path / Fill Path** (Layer menu, disabled without both an active path layer and an active raster layer) one-shot bake the path's geometry onto the raster layer's canvas via `paintEngine.ts`'s `strokePathOntoCanvas`/`fillPathOntoCanvas` (co-located there rather than in `pathGeometry.ts` because `pathGeometry.ts` must stay DOM-free — it's covered by `pathGeometry.test.ts`, and `paint/selection.ts`'s `clipToSelection` has a module-scope `document.createElement('canvas')` that crashes vitest's DOM-free unit-test environment the moment anything imports it, even transitively). **Select > Make Selection from Path** (`paint/selection.ts`'s `pathToSelection`) flattens the path's bezier curves into a dense point list (`flattenPathToPolygon`, standard cubic-bezier subdivision — polygon selections have no bezier concept of their own) and wraps it as an ordinary `{kind:'polygon'}` selection, which already does everything downstream for free.

Export: `exportImage.ts`'s flattened PNG/JPG/WEBP export rasterizes a path via `traceAnchors` (correct — flattened export has no vector concept regardless of format, same as text glyphs). `exportPsd.ts` writes a **real vector path** into the PSD (`vectorMask`/`vectorFill`/`vectorStroke`, not a rasterize fallback) — `ag-psd` genuinely supports Photoshop's native path-knot format, confirmed by an actual `writePsd`/`readPsd` round-trip during implementation: each `BezierKnot.points` is `[inHandleX, inHandleY, anchorX, anchorY, outHandleX, outHandleY]` in absolute page-pixel coordinates (`ag-psd` normalizes by width/height internally on write/read, so no manual scaling is needed on this side).

**A real, non-obvious gesture-timing bug found and fixed while building this**: Konva's Stage synthesizes a `dblclick` event from any two `click` events that land within its own timing window — **regardless of where on the stage they landed**. Since Pen anchor placement happens on pointerdown/up (not click), two ordinary clicks placing two *different* anchors in quick succession (a completely normal fast-clicking usage pattern, not just an automated-test artifact) could misfire Konva's synthesized dblclick and prematurely finish the path after only two anchors. `handleStageDblClick`'s pen branch now only treats it as a real double-click-to-finish if the last two placed anchors are actually at (near) the same spot — what an actual double-click always is — otherwise it's a no-op and the path stays open for more anchors.

**Explicitly out of scope**: path-layer masks (raster alpha clipping vector paint — the Layers panel's "Add Mask" action is gated against `type === 'path'` rather than silently no-opping), path-layer clipping (as a clip base or follower — `canBeClipBase` stays raster-only), path participation in the adjustment stack (nothing to filter until baked), Free Transform Path (bounding-box resize/rotate of a whole path), and compound multi-subpath paths (`PathLayerData.anchors` models exactly one open-or-closed subpath; `fillRule` is included forward-compatibly for whenever that lands).

**The Move tool drags pixel content trapped inside an active selection** on the active clean-patch layer (`StudioCanvas.tsx`'s `movingSelectionRef`): a pointerdown that lands inside the selection's own shape (`selectionContainsPoint`, a real point-in-path/mask test, not just the bounding box) cuts that region out of the layer's canvas into a scratch `pieceCanvas` and redraws it at the drag offset each move, restoring only the shrinking union of old/new rect each frame rather than the whole canvas; `onSelectionChange` re-fires every move too (`translateSelection`), so the marching ants track the moved content live instead of jumping at drag-end. A press-and-release with zero movement reverts the cut and skips history — otherwise every stray click inside a selection would count as a no-op edit. This is layer-content movement, not the layer-repositioning `x`/`y` drag the Canvas selection section below describes for text layers — it works today specifically because raster pixels are a canvas to redraw, where a text layer only has a Konva node to reposition.

**Select > Transform Selection** (menu item, `Studio.tsx`'s `transformingSelection` state) drops a free-transform box (Konva `Rect` + `Transformer`) around the selection's bounds; dragging/resizing/rotating it and committing with Enter (Escape cancels) reshapes the selection's own geometry via `transformSelectionMask` — an affine rotate+scale+translate around the box's pivot, rasterized through a canvas 2D transform since rotation/non-uniform scale can't be expressed by the vector `Selection` kinds. It **never touches pixel content**, only which pixels a subsequent paint stroke would be clipped to — mirrors Photoshop's Select > Transform Selection exactly. While it's active, all other marquee/lasso/paint pointer dispatch is suppressed so only the box's own Konva drag/Transformer responds.

**Quick Mask** (`Q`, or Select menu, `Studio.tsx`'s `quickMaskActive`) redirects every paint tool onto a scratch alpha-only canvas (`quickMaskCanvasRef`) instead of the active layer, shown as a red rubylith tint (`redrawQuickMaskOverlay`, built with a `destination-out` punch of the mask's alpha out of a flat red rect — no per-pixel JS loop needed even on live per-stroke redraws). Entering seeds the buffer from the current selection (`selectionToAlphaCanvas`); toggling off reads the buffer's alpha back into a real `Selection` (`alphaMaskToSelection`) via `StudioCanvasHandle.commitQuickMask()`. Painting in Quick Mask is deliberately unclipped by the outgoing selection (it's redefining it), so any tool — brush, eraser, gradient, shapes — becomes a selection-painting tool for free, the same "reuse the whole paint engine" trick `alphaMaskToSelection`'s doc comment calls out.

### Brush engine (`paint/brushTip.ts`, `paint/brushThumbnail.ts`, `BrushesPanel.tsx`)

Stamps are cached tip canvases (`getBrushTip`), keyed by size/hardness/shape/angle/roundness/colour (+ `maskId` for image tips). A dense stroke lays hundreds of stamps, so building the tip once and blitting it beats a per-stamp `createRadialGradient`+`arc`, and it's what makes non-round tips and imported image brushes possible at all. **Tips are rendered in their final colour, not tinted white-then-recoloured** — a `source-in` tint can only be applied to a whole canvas, so tinting the dirty sub-rect of a page-sized stroke buffer would wipe the rest of the stroke.

**Flow and opacity are genuinely separate**, Photoshop-style: `usePaintLayer` accumulates a whole stroke into a scratch buffer at `flow`, then composites that buffer onto the layer at `opacity`, restoring only the dirty rect (`compositeStroke`). Painting straight onto the layer at `opacity * flow` — which is what this used to do — lets overlapping stamps within one stroke blow past the opacity cap, making the two sliders indistinguishable. Also real: spacing, angle, roundness (elliptical/calligraphic tips), scatter, pull-string smoothing, square tips, and pressure independently driving size and/or opacity.

`BrushCursor.tsx` draws the live outline (size x zoom, angle/roundness, dashed inner ring at a soft tip's falloff, crosshair under 4px) as **SVG above the Konva stage**, so it can never reach exports or the layer stack. The OS cursor is hidden while a brush-sized tool is armed.

Brush presets (`src/lib/brushStore.ts`, idb-keyval `brush_presets`, schema-versioned) are plain parameter sets over that one engine — there is deliberately no separate "brush type", so an imported or duplicated brush is exactly as capable as a built-in. Built-ins live in code and are re-merged on load (only their `favorite` flag persists), so shipping a new one needs no migration. Panel thumbnails are drawn by the **real engine** (`renderBrushThumbnail` calls `strokeSegment`), so spacing gaps, scatter and pressure taper all show up truthfully. Imported images are baked to an alpha mask once at import (`imageToBrushMask`, alpha = 255 - luminance, existing alpha respected) rather than re-derived per stamp. **Favorites is a virtual folder** — a view over the flag, not a location.

**Note:** reading `e.target.files` and then setting `e.target.value = ''` before consuming it silently drops the upload — `FileList` is live, so clearing the input empties it. Snapshot with `Array.from(...)` first. This had already broken font upload in `FontsPanel`.

**Brush symmetry is real** (`PaintSettings.symmetry`, a Symmetry dropdown in the tool options bar for Brush/Pencil/Eraser): `usePaintLayer.ts`'s `applyStrokeSegment` mirrors each *segment* (not a post-hoc flip of the finished stroke) across the canvas center — `horizontal` flips left-right, `vertical` flips top-bottom, `both` draws all four. Only mirrors around the canvas center, not an arbitrary user-placed axis, and only for the three raw-stroke tools (not clone/filter-brush/liquify) — a real, honestly-scoped subset of what "brush symmetry" can mean.

**Liquify** (`paintEngine.ts`'s `liquify()`) is real — `push`/`swirl`/`pinch`/`bloat`/`crystalize`/`reconstruct` modes. The first five each compute a per-pixel *source sample offset* (a true warp, not a blend) with radial falloff, same getImageData/putImageData-over-a-bounding-box pattern as the filter brushes. `reconstruct` blends back toward a pristine pre-liquify snapshot instead — `StudioCanvas.tsx`'s `liquifySnapshots` registry captures one lazily per layer, on that layer's first-ever liquify edit (mirrors `paintCanvasRegistry`'s per-layer-id-not-page-id pattern), and it's cleared when the layer is deleted.

**Gradient** tool now goes foreground→background (`settings.bgColor`), matching Photoshop's default convention, instead of the old hardcoded foreground→transparent-white.

Grid (`showGrid`) and rulers (`showRulers`) are real, toggled from the View menu — grid is a Konva overlay layer at a fixed 100px page-space spacing; rulers are HTML overlays tracking `pos`/`scale` with tick labels every 100px.

### Persistence

Two separate IndexedDB stores, deliberately kept apart so painting never triggers a full-library rewrite:

- `workspaces_library` (existing, `App.tsx`) — chapter/page structure + image data URLs.
- `studio_<chapterId>` (`src/lib/studioProjectStore.ts`) — layers (with raster pixels as data URLs), TypeR script/styles. Autosaved 1.2s after the last layer/TypeR change *or* committed paint stroke (`Studio.tsx`'s `scheduleAutosave`/`flushAutosave`). Loaded on mount; raster layers hydrate lazily as each page is visited (`loadRasterLayer` polls briefly for the background image to finish loading — see `waitForImage` in `StudioCanvas.tsx`).
- `studio_versions_<chapterId>` — capped (10) full-copy version snapshots pushed on every autosave. No diffing/compaction; fine at this scale, revisit only if real usage shows storage bloat.
- `text_styles` (`src/lib/textStyleStore.ts`) — saved character/paragraph text styles. App-wide, not per-chapter (a style is meant to be reused across projects), which is why it isn't folded into `studio_<chapterId>`.

`studio_<chapterId>` is at **schema v5** (`STUDIO_SCHEMA_VERSION`; v2 added `autoWidth`/`letterSpacing`/`shadow`, v3 added `gradient`, v4 added `runs`, v5 made layers a tree). `migrateStudioLayers` runs on *any* mismatched version and every backfill in it is an idempotent `??`, so one pass takes v1–v4 straight to current — don't restructure it into a per-step chain without keeping that property. This matters because the renderer/panel read nested fields (`text.shadow`, `text.gradient`) directly, so an un-backfilled layer throws on open. v5 itself adds **no** backfill: its fields are all optional and absent *is* the pre-v5 behaviour, so `migrateLayer` only had to start recursing.

`SerializedStudioLayer` nests (`children?`) and carries pixels as `raster` (the layer's own) and `maskRaster`. The load-time strip and the autosave merge (`Studio.tsx`) both go through `layerTree`'s `mapTree`/`flattenTree`, which are generic over the node shape precisely so serialized layers reuse them instead of growing a second walker that could drift. The registries stay **flat, keyed by layer id** — nesting never reaches them.

Native project format: `.msp` (zipped JSON containing the full workspace tree + every chapter's studio data), `src/lib/mspFile.ts`. Export/import UI lives in `App.tsx`'s workspace list (not inside Studio, since it operates on a whole workspace).

### Export (`src/lib/exportImage.ts`, `src/lib/exportPsd.ts`)

- PNG/JPG/WEBP: `StudioCanvasHandle.getExportSnapshot()` captures background + full layer stack (raster layers as data URLs, text layers as structured data) for the active page; `compositeFlattenedImage()` flattens onto a canvas respecting opacity/blend/visibility, rendering text layers via canvas 2D (`fillText`/`strokeText`, with manual greedy word-wrap to approximate Konva's auto-wrap). JPG flattens onto white first (no alpha channel). `drawTextLayer` derives the text's **real** box before drawing — point text (`autoWidth`) is never wrapped and is measured, since its stored `width` is not its actual size; that box then drives wrapping, centring *and* the gradient vector, so all three stay consistent with the canvas.
- PSD: `exportPsd()` builds an `ag-psd` `Psd` object — one layer per `StudioLayer`, raster layers get a canvas, text layers get `LayerTextData` (editable in Photoshop; font family names pass through as-is, Photoshop substitutes if not installed — can't resolve that from a browser), per-character runs map onto its `styleRuns` so mixed-size/colour text stays editable rather than flattened, and gradient text adds a `gradientOverlay` effect (see Text layers above). `ag-psd` is **dynamically imported** (`await import('ag-psd')`) so it code-splits into its own chunk instead of bloating the main bundle (it's ~300KB alone) — its *types* are safe to import at top level, since `import type` is erased.
- `ExportDialog.tsx` wires both into the Project menu / `Ctrl/Cmd+E`.

Text export (TXT/DOCX/PDF) lives in `src/lib/textEditorExport.ts` — see the Text Editor section below.

### Canvas selection (Select tool)

`Studio.tsx` holds `selectedLayerIds: string[]`; **`activeLayerId` is derived from it** (the last member — the "primary"), not stored separately, so the two can't disagree. The single-layer panels (Text, Adjustment), the layer shortcuts and the edit target all key off the primary; the set drives multi-layer operations.

- Click selects, **Shift/Ctrl-click toggles** (canvas *and* Layers panel), click on empty canvas deselects.
- **Drag on empty canvas marquee-selects** objects. This is why only the Pan tool drags the stage natively — the Select tool's drag is the marquee, so panning while it's active uses the same Space-hold / middle-drag path every other tool already had.
- Delete removes the whole selection (`handleDeleteLayers` filters out the background and locked layers rather than special-casing each call site).
- **Only text layers participate.** They're the only layers with Konva nodes and an `x`/`y` in the data model — see "Move tool only repositions/relocates text layers" in Known gaps. (The Move tool's other job, dragging pixel *content* trapped inside a selection on a clean-patch layer, is a separate mechanism — see Selection model above — and isn't gated on this data-model gap, since it redraws the layer's own canvas rather than moving a Konva node's `x`/`y`.)

Two things here are non-obvious and were both found by testing rather than reasoning:

- **Konva's Transformer already moves every attached node** when a multi-selection is dragged, and it derives the combined bounding box from its node list. Propagating the drag delta to the other selected nodes by hand double-applies it and the followers overshoot. Each node just commits its own position in `onDragEnd`.
- A text layer's hit area is a `Rect`, and so is the page's drop-shadow backing — the stage's "did I click empty canvas?" test goes by class name, so the hit rect carries `TEXT_HIT_NAME` and is excluded explicitly. Without that, clicking text counted as clicking background and cleared the selection the click had just made.

A finished marquee drag also fires a trailing stage click that would clear the selection it just made; `objectMarqueeConsumedRef` swallows it, mirroring `textDragConsumedRef`'s handling of the same problem for the Text tool.

A text layer's `draggable` prop excludes `spaceDown`, matching the Stage's own draggable calc — without that, holding Space to pan while dragging a text layer fired **both** Konva's native node-drag and the manual space-drag pan loop from the same gesture, reading as the canvas jumping under the text mid-drag.

### Text layers (`TextLayerNode.tsx`, `textLayout.ts`, `textRuns.ts`, `TextPanel.tsx`, `textGradient.ts`)

A text layer is a layer-wide style **plus** `runs: TextRun[]` — per-character overrides. Photoshop's split decides what lives where, and it's the same split ag-psd's `styleRuns` uses:

- **Per-character (`TextRun`)**: font family, weight, bold/italic, size, colour, tracking, kerning, baseline shift.
- **Layer-level**: stroke, shadow/glow, gradient (layer *effects*), and align/lineHeight/wrap (paragraph properties).

Two modules own the invariants, and nothing else may duplicate them:
- **`textRuns.ts`** owns the run invariant — runs are contiguous and cover `content` exactly. Never hand-edit `runs`; go through `normalizeRuns`/`applyToRange`. Plain text is `[]`: a lone override-free run carries nothing the layer style doesn't, so it collapses (adjacent identical runs merge too, or the array fragments to one run per character after a few edits). `resolveRunStyle` is the **only** place default-vs-override precedence lives.
- **`textLayout.ts`**'s `layoutText()` owns wrapping, the box, alignment, baselines and run positions, and is shared by the canvas *and* the raster exporter. They each used to wrap independently, which is exactly how point text ended up exporting wrapped when it never wraps on screen.

**Point vs area (box) text**: `TextLayerData.autoWidth` — point text grows to fit and never wraps; area/box text wraps at its authored `width`. Both share one Transformer with all 8 resize handles + a rotation handle (`StudioCanvas.tsx`); a corner drag scales `width` (reflow, via `layoutText`) and `fontSize` (glyph size) together rather than baking a Konva scale onto the node, so the layer's stored data stays the source of truth after every resize. Double-clicking a handle auto-fits a box layer's `width` tightly to its content (`layoutText({...text, autoWidth: true}).width`); triple-clicking inside editing text selects all (native textarea `select()`, gated on `e.detail === 3`). Area text can optionally set `fixedHeight`, in which case content that would overflow it is actually clipped at the box's bottom edge — both on canvas and in flattened PNG/JPG/WEBP export, not PSD export, which writes native editable Photoshop text and never calls `layoutText` — and shows a small interactive ⊞ indicator, still driven by the same derived `layout.overflowing` (never a stored field — `textLayout.ts`'s own docstring calls out `layoutText` as the single source of truth for wrapping, the box, alignment and baselines, so nothing else may keep a second copy of "does this overflow"). Freshly-typed content that reads as majority-Arabic-script (`textLayout.ts`'s `isArabicMajority`) defaults a still-empty layer to right alignment the moment it's typed — a one-time default on the empty→non-empty transition only, so it never fights a later manual change.

**Resizing reflows live, not just on release**: `TextLayerNode.tsx`'s `onTransform` (fires every drag frame, not only `onTransformEnd`) converts the node's current scale into real `width`/`fontSize` data and zeroes the Konva scale back to 1 immediately, every frame — so the *next* frame's `layout` (and thus the actually-rendered wrapped lines) reflects the true in-progress size, rather than Konva just visually stretching the cached glyphs until release. No history label on either handler (matches the existing continuous-drag convention, e.g. opacity), so live-dragging doesn't spam an undo entry per frame.

**Point and area text scale *different* things on a handle drag, matching Photoshop exactly.** Point text has no frame of its own — resizing it *is* resizing the type, so `scaleY` converts to `fontSize` (unchanged from the original behaviour). Area text has a real frame independent of its type size: resizing changes the box only (`width` from `scaleX`, `fixedHeight` from `scaleY` — converting/updating a fixed frame height the same way a drag-created box gets one, see below) and reflows the *existing* `fontSize` into it. The branch is `text.autoWidth ? ... : ...` in both `onTransform` and `onTransformEnd`; area text's font size never moves, not even by 1px, no matter which of the 8 handles is dragged.

**`fontSize` is always an absolute, stored value — never derived from box size** — and `onTransformEnd`'s area-text branch (`!text.autoWidth`) carries a permanent `import.meta.env.DEV`-only assertion enforcing it: if a future edit to that handler ever lets `fontSize` slip into the patch for an area layer, it throws `REGRESSION: area text resize must never modify fontSize` immediately rather than silently reintroducing "the box resize scales the type" bug. Dev-only so a real resize in production can never hard-fail over this — the assertion's job is catching the regression in `npm test`/local dev, not policing production input.

**The text Transformer's 8 handles aren't all the same size.** `StudioCanvas.tsx`'s `anchorStyleFunc` sizes the four corner anchors (which resize both dimensions) at 8×8px and the four edge anchors (which resize one) at 6×6px, so the distinction reads at a glance instead of eight identical squares — Konva already assigns the correct per-anchor resize cursor (diagonal for corners, axis-aligned for edges) on its own, so only sizing needed overriding.

**Point ↔ Area conversion is a real, undoable command** — `LayersPanel.tsx`'s right-click menu (Convert to Area Text / Convert to Point Text, gated on the layer's current `autoWidth`) calls `Studio.tsx`'s `handleConvertTextMode`. Area → Point just flips `autoWidth` and clears `fixedHeight` (meaningless for point text); Point → Area seeds the new frame's `width`/`fixedHeight` from `layoutText({...text, autoWidth: true})` — the exact same natural-size call the auto-fit-width double-click already uses — so the box starts sized to precisely what's currently on screen instead of jumping to an arbitrary default.

**Drawing an area box captures both dimensions, not just width.** `StudioCanvas.tsx`'s `textDragPreview` state renders a live dashed rect + a "W: _ px / H: _ px" readout (counter-scaled by `1/scale` so it reads a fixed size on screen at any zoom) while the Text tool drag is in progress — previously only the width was ever read off the drag (`Math.abs(p.x - start.x)`); the vertical delta was silently dropped, so a drag-created box could never get an intentional height, only whatever `layoutText` naturally produced. `onAddTextLayer`/`createTextLayer` now take an optional `boxHeight` alongside `boxWidth`, which becomes the new layer's `fixedHeight` at creation — the dragged rectangle *is* the frame, exactly Photoshop's convention, not just a starting width that auto-grows. The same dead-zone-to-click-vs-drag threshold now checks either dimension (`width >= 12 || height >= 12`), so a mostly-vertical drag still means "draw a box."

**A selected (not editing) text layer shows the same W×H readout** as the drag preview, plus a dashed Transformer border (`borderDash`, matching every other selection/preview overlay's dashed convention instead of Konva's default solid one) and the ⊞ overflow glyph at bottom-*center* (not bottom-right — Photoshop's own placement). Hovering the box's own body (not a Transformer handle, which sits on top and always wins the hit-test first) sets a `cursor-move` class on the canvas container via `TextLayerNode`'s new `onHoverChange` prop bubbling a boolean up to `StudioCanvas.tsx`'s `hoveringTextBody` state — dragging the body itself (as opposed to a handle) still only moves the layer, per the existing `onDragEnd` (`x`/`y` only, size/content untouched).

**The ⊞ overflow indicator is a small clickable control, not just a glyph.** It renders a light background square with a thin dark border (both sized in `/scale` units for a fixed ~16 on-screen px footprint at any zoom — this file's per-value-division convention, the same one the W×H readout above already uses, not a counter-scaled wrapper Group) behind the `⊞` character, straddling the box's bottom-center edge. A single click/tap is presently a deliberate no-op (`cancelBubble` + `preventDefault` + `stopPropagation`, so it never reaches the parent Group's own click/dblclick handlers and therefore never selects/deselects the layer or enters edit mode), marked with a `// TODO: text threading` comment at the indicator's `onClick`/`onTap` handlers in `TextLayerNode.tsx` — the eventual hook for linking one box to another so overflow content flows between them. A double-click/tap auto-fits `fixedHeight` tightly to the content's natural height (`layoutText(text).height`, floored at 20, independent of the *current* `fixedHeight`) via `Studio.tsx`'s `handleAutoFitTextHeight`, pushed through a labeled `updateLayers(..., 'Auto-Fit Text Box Height')` call so it's a real, undoable history entry — a *different* mechanism from the existing Transformer-handle double-click above, which fires on the Transformer node itself, only ever touches `width`, and stays deliberately unlabeled. Hovering the indicator sets a `cursor-pointer` class on the canvas container (`StudioCanvas.tsx`'s `hoveringOverflowIndicator` state, checked ahead of the box-body `hoveringTextBody`/`cursor-move` in the cursor ternary, since the indicator sits inside the body's own hit area). **The fixedHeight clip itself is scoped to a nested inner `Group` wrapping only the run glyphs** (`TextLayerNode.tsx`, via Konva's native `clipX`/`clipY`/`clipWidth`/`clipHeight` rather than `clipFunc`) — not the outer per-layer Group, which also carries UI chrome (the W×H readout, the indicator itself, per-line hit rects) that has to stay visible/clickable regardless of what's being clipped away below the frame. Konva clip regions nest via ordinary canvas `save`/`clip`/`restore`, so this composes for free with the outer Group's own Type Region `clipFunc` — no manual path-combining needed. `exportImage.ts`'s `drawTextLayer` applies the same rect as a second sequential `ctx.clip()` call after the existing Type Region clip, in the same `ctx.save()`/`ctx.restore()` scope — safe there specifically because that function draws only glyph content, with no UI overlays to accidentally clip.

**A floating contextual toolbar follows the box while editing** (`FloatingTextToolbar.tsx`): font family, size, colour, bold/italic, alignment — positioned directly under the box, flipping above it when there isn't `TOOLBAR_HEIGHT + GAP` of room below (checked against `containerSize.height`, the same value the Stage itself sizes to). Its own `onMouseDown` calls `preventDefault()` so clicking a control doesn't blur the editing textarea (which would otherwise end the edit via the textarea's existing `onBlur`). **This box-following position, and only appearing once a layer is being edited (not during the draw-before-release gesture), are both deliberate** — a request to dock it permanently at the canvas bottom and show it mid-draw was evaluated and declined, since it's a working, intentional design rather than a bug; don't "fix" it without a real product decision to change it.

**A freshly-typed Arabic layer's caret actually starts on the right, not just the *text* right-aligning.** The editing textarea gets `dir={text.align === 'right' ? 'rtl' : 'ltr'}` — right alignment is this app's existing proxy for "this layer is RTL" (see `isArabicMajority`'s auto-default below), but alignment alone doesn't reverse caret/arrow-key direction; `dir="rtl"` is what actually does. A still-empty box defaults to `center` align, so it starts `ltr` and only flips once Arabic content is typed and align auto-switches — mirroring the same heuristic, not a separate one.

**Shift/Alt during a corner drag are live, not sampled once at drag-start**: `StudioCanvas.tsx` tracks `shiftHeld`/`altHeld` via window keydown/keyup (mirroring the existing `spaceDown` pattern, plus a `blur` listener so an Alt-tab mid-drag can't leave a modifier stuck "on") and passes them straight through as the text Transformer's `keepRatio`/`centeredScaling` props. Konva re-reads both on every transform-computation frame, so toggling the key mid-drag changes behavior mid-drag: Shift constrains the box (and, since `fontSize` scales with `scaleY`, the type size) proportionally; Alt resizes around the box's own center instead of the opposite corner/edge. Scoped to the layer Transformer only (its `nodes()` are always exactly the selected text layers) — the separate Select > Transform Selection Transformer doesn't get this, since that's reshaping selection geometry, not a text box.

**Per-line overrides are a third styling tier**, above per-character runs: `TextLayerData.lineOverrides?: Record<number, LineStyleOverride>`, keyed by a line's index in the *current wrapped layout* (so a reflow that shifts line counts can shift what an override applies to — an accepted trade-off since line overrides are an occasional balancing tool, not something edited every keystroke the way runs are). `textRuns.ts`'s `resolveLineStyle` applies on top of a run's already-resolved style — line wins over run wins over layer default. Click a line on canvas (only while the layer is selected and not being edited — independent of the editing textarea's own character-range selection) to target it; `TextLayerNode.tsx` renders one invisible hit `Rect` per `layout.lines` entry. `layoutText()` re-measures an overridden line's pieces (a line override can change `fontSize`/`letterSpacing`, which the pre-wrap widths used for every *other* line's alignment don't reflect) so its own wrap width/alignment stay self-consistent. Flows through PNG/JPG/WEBP export for free via the shared `layoutText` path; **PSD's `styleRuns` are per-character only**, so line overrides don't carry into PSD export yet.

**Konva has no rich text** — `Konva.Text` renders one uniform style. So `TextLayerNode.tsx` renders a `Group` with **one `Konva.Text` per positioned run**, placed by `layoutText`; Konva still paints the glyphs, we only position them. A custom `sceneFunc` would have meant reimplementing stroke/shadow/gradient painting. The Group is the interactive/transform target and carries a `transparent`-filled `Rect` for hit area and bounds (a transparent fill still reaches the hit canvas, where Konva substitutes its own colour key), so clicking gaps between glyphs selects the layer and the Transformer frames the text box rather than glyph extents.

Load-bearing details:
- `measureRunText` deliberately uses **Konva's own formula** (`measureText(text).width + letterSpacing * length`, measuring *without* native `ctx.letterSpacing`) — Konva draws spaced text letter-by-letter with that advance, so matching it is what keeps a run's laid-out width equal to the width Konva renders, which is what lets runs butt up against each other.
- **Kerning is modelled as extra advance *before* a run.** A manual kern is applied at a caret position between two characters, and a caret position is exactly a run boundary — that's what makes it faithful rather than an approximation.
- Line height comes from the **layer's** `fontSize`, so a single big run doesn't reflow the whole block (matching what `lineHeight` has always meant here). Runs share a baseline, so a bigger run's em box starts higher.
- Konva's `fillPriority` defaults to `'color'`, so a node with both `fill` and gradient stops silently renders the **flat colour**; it must be set to `'linear-gradient'` when a gradient is on.

**Gradient text is real** (`TextLayerData.gradient`). `textGradient.ts`'s `gradientVector(w, h, angleDeg)` is shared by canvas and exporter; it *projects* the box onto the gradient direction rather than running corner-to-corner, so the ramp spans the full box at any angle. Angle is degrees clockwise from left-to-right in **screen coords (y down)**, so 90° = top-to-bottom. The ramp is computed once on the **layout box** and each run subtracts its own offset (Konva gradient points are node-local) — without that subtraction every run would restart the ramp. PSD carries the gradient as a `gradientOverlay` **effect** (how it's done by hand in Photoshop, and still editable there), with `style.fillColor` left as the flat colour underneath. ag-psd normalizes gradient stop `location`/`midpoint`/`opacity` to **0..1** and scales them on write — they are *not* raw 0..4096 PSD units. Photoshop's angle is counter-clockwise/y-up, so `exportPsd` negates ours.

**Character selection** is the editing `<textarea>`'s own `selectionStart`/`selectionEnd` — there's no separate selection model. It's lifted to `Studio.tsx`'s `textSelection` so `TextPanel` (a dock sibling) can style it. With a range selected the character controls write run overrides; with no range they apply layer-wide (what Photoshop's Character panel does when the layer rather than a range is selected) — and a layer-wide change also *clears* that key's run overrides, or the new default would be masked by runs and the control would look broken. Triple-click-to-select-all is handled on the textarea, not the Konva node: once editing starts the textarea sits above the stage, so the third click never reaches the shape.

`reflowRunsForContent` re-anchors runs when `content` changes, diffing by common prefix/suffix — the textarea only hands us the new string, not an edit operation, so without it styled spans would slide off their characters as you type.

**Character and paragraph styles** (`src/lib/textStyleStore.ts`) apply at **layer level**, not to a selection — `CHARACTER_STYLE_KEYS` includes layer-only fields (shadow/gradient/stroke), so routing them through runs would half-apply them.

**Saved character and paragraph styles are real** (`src/lib/textStyleStore.ts`, idb-keyval `text_styles`, schema-versioned). A character style captures appearance (font/size/colour/bold/italic/tracking/stroke/shadow/gradient); a paragraph style captures layout (align/lineHeight/autoWidth). `CHARACTER_STYLE_KEYS`/`PARAGRAPH_STYLE_KEYS` are the single source of truth for both capture and apply — applying one touches **only** its own subset, which is the whole point of the split (restyle layout without overwriting the font). Capture and apply both `structuredClone`, so a saved style never shares its nested `shadow`/`gradient` object with a layer.

### TypeR (scripted lettering)

`studioTypes.ts`'s `parseTyperScript()` + `TyperPanel.tsx`. Paste a script, arm it, click bubbles to stamp lines in order with per-line styles matched by prefix (longest prefix wins; empty-prefix style is the catch-all).

Ported from the real TypeR 2.5 extension's documented behavior (see `src/assets/claude.md` for the original algorithm description, and `src/assets/mangastudio (1).html` for a working reference implementation):
- `##`-prefixed lines are ignored (notes).
- `//`-prefixed lines continue (append to) the previously placed line rather than starting a new one.
- `Page N` control lines (English or Arabic, incl. Arabic-Indic digits) tag the next real line with a page hint; `Studio.tsx` auto-switches pages as the armed script advances onto a hinted line (matches by number extracted from the target page's filename, falling back to 1-based position).
- A line fully wrapped in `**bold**`/`<b>...</b>` or `*italic*`/`<i>...</i>` overrides that style's weight for just that placement.
- Styles have an optional `folder` field for organizing the panel into collapsible groups — **folder does not affect prefix-matching priority** (simplified from the original "focused folder" UI concept, which doesn't exist here); matching is purely longest-prefix-first across all styles.

**Multi-Bubble mode is real**: toggle it on in the TypeR panel (a "Layers"-icon button next to Arm, or `Ctrl+Shift+M` — the one TypeR shortcut that *is* a fixed keybinding, unlike Type Region's deliberately-unbound arm toggle below, since toggling a mode has nothing to collide with mid-gesture the way an armed click does), and arming switches the active tool to Rectangular Marquee instead of Text. Draw a rect per bubble and click "Add Bubble" to queue it (rendered as a distinct amber dashed overlay, `StudioCanvas`'s `queuedBubbleRects` prop, alongside the normal white live-selection outline) — then "Place All" stamps each queued rect's line, in one `updateLayers` call (`Studio.tsx`'s `handleAddBubbleRect`/`handlePlaceAllBubbles`). **Not implemented**: per-character rich text *from a script* — bold/italic overrides still apply to the whole placed layer. `TextLayerData` now has a run model (see Text layers above), so this is no longer blocked on the data shape; it's that `parseTyperScript` only marks a whole line bold/italic, so nothing emits partial runs.

Each capture snapshots **which script line it was drawn against**, not just the rect (`{ rect, lineIndex }`, `Studio.tsx`'s `multiBubbleRects`) — `handleAddBubbleRect` auto-advances `typerIndex` after every capture, the same way a single armed canvas click does, so jumping to a different line in the panel's own line list *between* two captures sticks: "Place All" replays each capture's own snapshotted line/style rather than re-deriving position from sequential order at fill time. If a captured line carries a `pageHint` (a `Page N` control line preceded it), `handlePlaceAllBubbles` stops *before* placing that capture — its rect was drawn on whatever page was active at capture time, so placing it after switching pages would misplace it — switches to the hinted page, and drops the rest of the queue, mirroring the real extension's "reaching a Page N marker stops the fill" behavior. The queue's "−" button removes the most recent capture one at a time (LIFO); holding it past 1s turns it red as a warning and past 2s clears the whole queue instead (`TyperPanel.tsx`'s `onRemovePointerDown`/`Up`/`Leave`, a plain `setTimeout` pair, not a separate confirm dialog).

**Every parsed line is listed and individually clickable, not just the current one** (`TyperPanel.tsx`, a scrollable numbered list built from the same `parseTyperScript()` result the placement logic reads). Clicking a row calls `onIndexChange(i)` directly — a plain set, not an advance — so jumping from line 1 to line 7 goes straight there without visiting the lines in between; the current row auto-scrolls into view (`scrollIntoView({block:'nearest'})`) on every `index` change. This is in addition to, not instead of, sequential advance: placing a bubble on canvas (`Studio.tsx`'s `handleAddTextLayer`/`handlePlaceAllBubbles`) still does its own `index + 1` afterward, unaffected by how the position got there. There's no dedicated advance keybinding (no Ctrl+Enter or similar) — placement only ever happens via an armed canvas click, matching Type Region's own "no keyboard shortcut so it can't collide" reasoning below. A placed line gets a ✓ (`Studio.tsx`'s `typerPlacedIndices`, a `Set<number>` of already-stamped line indices, checked on both the single-click and Multi-Bubble placement paths) and dims in the list — this tracks "is this line's content actually sitting on the canvas somewhere," not session/arm progress, so it survives jumping the cursor backward and isn't touched by Reset Progress; it's cleared only when the script text itself changes, since line indices stop meaning the same thing once that happens (not persisted, mirroring `typerIndex`'s own session-only lifetime).

**A style can be disabled** without deleting it (`TyperStyle.enabled`, an eye/eye-off icon on each style row in `TyperPanel.tsx`) — `parseTyperScript`'s `matchStyle` skips a disabled style's prefix entirely (falls through to the next candidate, then `defaultStyleId`, then the empty-prefix style), while a disabled style can still be reached *as* that default/catch-all. Missing `enabled` on data saved before this field existed reads as enabled (`s.enabled !== false`), so it needed no schema bump or migration step.

**Export Folder** (a second icon next to the existing "export all" button) exports one folder's own styles as JSON via the same `swal` `input:'select'` single-choice picker this app already uses elsewhere (`LayersPanel`/`BrushesPanel`'s row context menus) — deliberately one folder at a time, not a multi-select, since `swal`'s plain `<select>` input has no clean multi-select story here. It does not recurse into sub-folders' own styles — same flat `folderId` scoping every other per-folder operation in this panel already uses.

**TypeR can detach into its own floating window** (`TyperFloatingWindow.tsx`) — the first floating panel anywhere in this app; there is still no general floating-panel system, and this is deliberately scoped to TypeR rather than one. A pop-out button in `TyperPanel`'s own header (or Window > Float TypeR) swaps the docked tab's content for a "Dock it back" placeholder and mounts the same, completely unforked `TyperPanel` inside the floating window instead — the two are mutually exclusive, never both mounted at once, so `typerIndex`/`typerArmed`/`typerScript` (which live in `Studio.tsx` regardless, since `StudioCanvas` reads them for canvas-click placement either way) can't fork across two live instances. Dragging is the same manual window-level `mousemove`/`mouseup` idiom `StudioCanvas.tsx`'s Space-hold pan already uses (a ref tracks the in-progress delta so `TyperPanel`'s own internal state and memoized script parse don't thrash mid-drag; the final position commits to state once on mouseup, clamped to keep a grabbable sliver on-screen). Floating state and position persist per chapter via `localStorage` (`studio_typer_floating_<chapterId>` / `..._pos_<chapterId>`), mirroring `DockContext`'s own debounced-write pattern for the active dock tab. No Escape/click-outside dismissal — unlike `ToolFlyout`/`AppContextMenu`, this is a persistent workspace element, not a transient popup.

**Type Region is a separate, freehand extension of TypeR — not a replacement for the panel above.** The panel's own arm state and its `placeInSel`-equivalent/`mqAuto`-equivalent/`mbFill`-equivalent flow (`handleAddTextLayer`'s TypeR branch, `handleAddBubbleRect`/`handlePlaceAllBubbles`, `parseTyperScript`) are untouched by it. Type Region has its own arm toggle (`Studio.tsx`'s `typeRegionArmed`, a `StudioToolbar` button, deliberately no keyboard shortcut so it can't collide with the panel's own) and a different job: turning a selection made with *any* selection tool into a live text container, immediately, for direct freehand typesetting rather than a scripted pass. While armed, `StudioCanvas.tsx`:
- Intercepts a pointerdown that lands inside an existing selection (`selectionContainsPoint`), ahead of whatever the currently active tool would otherwise do with that click, and hands the shape to `Studio.tsx`'s `handleCreateTypeRegion`.
- Also auto-converts the instant a **new** selection completes — Rectangular/Elliptical Marquee, freehand/Polygonal/Magnetic Lasso, and Magic Wand (not row/col/Crop/Slice, and not pen — Make Selection from Path is a menu action, not a drag/click gesture with its own natural "just completed" moment, so it stays click-inside-only) — one continuous gesture, no separate "Add Bubble" click. Polygonal/Magnetic Lasso hook into their own commit point (`commitLassoPolygon`, fired by Enter or closing the loop) rather than a pointerup, since they're click-accumulate gestures. Magic Wand has no drag-end either (a single click), so `usePaintLayer.ts`'s `pickMagicWand` now **returns** the selection it computed instead of only calling `onSelectionChange` — the caller needs the just-picked shape synchronously, and reading the `selection` prop back in the same tick would still see the pre-click value.

`handleCreateTypeRegion` sizes the new text layer to `paint/selection.ts`'s `selectionBounds(shape)` (any selection kind's bounding box, computed directly for rect/ellipse/polygon rather than rasterizing, since `mask` already carries its own). A non-rectangular shape also gets a `TextLayerData.clipShape` (`{kind:'ellipse'|'polygon', ...}` in the same image-space coords as `x`/`y`) — a rect needs no clip (the frame itself already is the rect), and a `mask`-kind selection has no clean vector form to persist, so it falls back to a plain rectangular container at its bounds instead of storing anything. `clipShape` drives a Konva `clipFunc` on the text layer's `Group` (`TextLayerNode.tsx`, translating the stored page-space shape into the Group's local space by subtracting `text.x`/`y`) and the identical shape clips `exportImage.ts`'s flattened PNG/JPG/WEBP export (there, `ctx` is still in page-space at that point, so no translation is needed). The shape's dashed outline is a **sibling** of the main text `Group`, not a child of it — the main Group is `visible={false}` while editing, which is exactly when the outline needs to stay visible so the container's real shape reads behind the editing textarea. `pathForSelection` is exported from `paint/selection.ts` (previously module-private) so both the paint-clip path and this one build the exact same `Path2D`. **PSD export doesn't carry `clipShape`** — `ag-psd`'s vector-mask mapping wasn't attempted for this; a Type Region text layer round-trips through PSD as an unclipped rectangular text layer, still editable.

### Translation Preview panel

`TranslationPreviewPanel.tsx` — lists every text layer across every page in the chapter (reads `layersByPage` directly, no extra loading needed since it's already all in memory), with jump-to-bubble, cross-page search/replace, and per-dialogue status (`draft/translated/reviewed`) + comment fields on `TextLayerData`. ### Menu bar (`menu/`)

**A real multi-level Photoshop-style menu**, not the flat single-depth dropdown it used to be. `MenuItemDef` (`menu/menuDefinitions.ts`) gained a recursive `submenu?: MenuItemDef[]` field; `Menu.tsx` renders it recursively via `MenuItemRow`, which manages its own nested-submenu open state and edge-flips (right→left) when it would clip the viewport's right edge — reusing the same "measure the real rendered rect via `getBoundingClientRect`, then nudge/flip" idea `ToolFlyout.tsx` already proved out for tool-group flyouts, rather than hand-estimating position from the Tailwind classes. A submenu opens on hover (the parent row's wrapper carries the popover as a DOM descendant, so moving the pointer diagonally into it never fires the wrapper's own `onMouseLeave` — no separate close-grace timer needed) or on click/tap, which is what makes it work identically on touch. `buildMenus()` now returns ten menus (`Project/Edit/Select/View/Image/Layer/Text/AI/Window/Help`), up from eight — `Image` and `AI` are new.

**A real, serious bug found while building this**: the menu bar's own wrapper div had `overflow-x-auto` with `overflow-y` left unset. Per the CSS Overflow spec, an explicit non-`visible` value on one axis forces the *computed* value of the other to `auto` too — and that coercion still applies even if you explicitly set the other axis to `'visible'`, since `'visible'` paired with a non-`'visible'` sibling isn't a valid combination at all. The practical effect: every dropdown/submenu silently clipped to the bar's own ~32px height, for every real user — a plain DOM/visibility check couldn't catch it, because Playwright's own actionability checks auto-scroll a clipping ancestor into view before clicking/hovering, which is exactly what made the bug invisible under automated testing while being totally broken for an actual mouse user. Fixed by dropping the `overflow-x-auto` entirely (ten short menu labels fit down to a 768px-wide viewport without it).

**Real vs grayed, by design, not oversight** — every item either calls a real function or ships `disabled` (never a silent no-op): real wiring covers Cut/Copy/Paste (`lib/layerClipboard.ts`, reusing `layerTree.cloneSubtree` + `StudioCanvasHandle.clonePaintCanvases`/`cloneMaskCanvases` — the exact pairing this doc already calls load-bearing for Duplicate), Merge Down/Merge Visible/Flatten Image, Rotate Canvas (`StudioCanvasHandle.rotateCanvas`, mirroring `commitCrop`'s shape — text layers reposition and rotate to match, path layers don't, the same pre-existing scope limit Crop already has), Save Project (flushes the debounced autosave immediately), Find & Replace (opens the Translation panel's existing search), the whole Text menu's Bold/Italic/Size/Align/RTL/LTR (`textRuns.ts`'s `applyCharPatch`/`resolveCharValue`, shared with `TextPanel.tsx` so the two precedence rules can't drift apart), Content-Aware Fill and Liquify (switch to the existing real tools, no dialog), and Export as .msp (threaded down from `App.tsx`'s existing workspace-level export). Permanently grayed: anything requiring a subsystem that doesn't exist — New/Open Project, Open Recent, Guides, Safe Area, Snap to Grid/Guides, Image Size/Canvas Size, granular per-channel pixel locks, AI bubble detection, Documentation (no URL to link to, and one must not be invented) — plus `Apply Filter`'s "fake" siblings (Smart Sharpen, Reduce Noise, Color Halftone, Glowing Edges) that were never committed as real filters alongside the eight that were (see Filter pipeline below).

### Panel column (`dock/`)

**The right column is a real Photoshop-style stacked panel system**, not a single-active-tab dock (an earlier design; `DockContext.tsx`/`RightDock.tsx` are gone). `dock/PanelLayoutContext.tsx` tracks, per panel id, its `order` position, `visible`, and `collapsed` state — persisted to `localStorage` under `studio_panel_layout_<chapterId>` (schema-versioned, debounced), scoped per chapter like the dock key it replaced. `dock/PanelStack.tsx` renders every currently-visible panel, in the user's own order, as a `dock/CollapsiblePanel.tsx`. Any subset of Color/TypeR/Translation/Layers/Brushes/Fonts/Adjustment/Text/History can be visible **simultaneously** — this is the structural fix for the old "Layers list disappears when you switch tabs" bug: there's no "active tab" to switch away from anymore. Color/TypeR/Translation/Layers start visible by default (Translation collapsed); Brushes/Fonts/Adjustment/Text/History start **absent** (not just collapsed — see below), toggled on via Window menu.

**`CollapsiblePanel` owns one shared header** for every panel: a drag handle (native HTML5 DnD, reordering via `PanelLayoutContext.reorder`), a real `<button aria-label="Collapse/Expand {title} panel">` chevron — not a plain clickable `<div>` with no accessible name, which is exactly the gap an e2e test caught (see below) — an optional `⋯` button (`onMenu`, only rendered when a panel actually has a real action to put there: Layers gets New Layer/New Blank Layer/Flatten Image/Merge Visible via a `swal` `input:'select'` dialog, the same pattern `BrushesPanel`'s preset menu already uses; most panels get none rather than a fake one), and double-click-to-maximize. **A double-click still fires two ordinary `click` events first** (same DOM footgun `TextLayerNode`'s pen-tool dblclick-detection already works around, just for a different gesture) — a naive `onClick` would toggle collapse twice before `onDoubleClick` fires; the single-click action is debounced (`DOUBLE_CLICK_WINDOW_MS`) so a fast second click cancels it outright instead of visibly flickering. Collapse is a real animated `max-height` transition, measured live via `ResizeObserver` (not the old system's instant Tailwind-class swap) so it stays correct as a panel's own content grows/shrinks.

**Layers is `grow` but not special-cased out of collapsing.** `grow` only changes *how* it fills space while expanded — `flex-1` with its own internal scroll, instead of the usual measured-height animation — never *whether* it can collapse. Layers was briefly made permanently uncollapsible when this was first built (reasoning: "never fully hide the list"), which broke a real, pre-existing workflow an adjustments.spec.ts e2e test encoded — temporarily collapsing Layers (and Color, and whatever else is crowding the column) to give a cramped panel like Adjustment's 200px-tall Curves graph room. Collapsing is a normal, reversible, user-initiated action; the historical bug this rewrite exists to avoid was the panel *auto-hiding on an unrelated click*, which collapse-via-its-own-chevron isn't.

A `grow` panel's own `flex-1 min-h-0` needed a real `min-h-[220px]` floor: nested inside the stack's `overflow-y-auto` column, a bare `flex-1` shrinks toward zero *before* the column starts scrolling — tall panels above it (TypeR, expanded by default) could squeeze Layers down to almost nothing rather than the column just scrolling past them. Caught by an e2e test that drags a layer onto a group: the drop target's row had shrunk to an unusable sliver.

**Every panel component takes a `hideTitle` prop** so `CollapsiblePanel`'s own header doesn't duplicate the title each one already renders via its own `StudioPanel` usage (`StudioPanel.tsx` grew the `hideTitle` support itself — hides just the title text, and skips its whole header row entirely if there are no `actions` to show either, rather than leaving a blank strip). `ColorPanel`/`LayersPanel` dropped their bespoke chevron code in favor of it.

**Selecting a layer never reveals its Text/Adjustment panel.** `selectLayer`/`selectLayers` (`Studio.tsx`) only select — opening a layer's full settings (the panel itself, or the Layers row's own opacity/blend/mask/clip strip) is a separate, explicit gesture (`openLayerSettings` calls `PanelLayoutContext.reveal(id)`, the closest equivalent to the old dock's "select this tab" — makes a panel visible *and* expanded). This predates the panel-stack rewrite and didn't need to change: the underlying goal (a click never hides the Layers list) is now structural rather than a special case, since nothing is ever hidden by *anything else* becoming active.

**One real architectural consequence of dropping single-active-tab semantics**: panels no longer auto-hide each other. TypeR, expanded by default, now stays visible *alongside* Adjustment when an adjustment layer is selected — where the old dock would have shown only whichever tab was active. An existing Curves-editor e2e test had to be updated to also collapse TypeR (not just Color/Layers) to get the same usable room it used to get for free, and to `scrollIntoViewIfNeeded()` before computing a raw click coordinate — `page.mouse.click(x, y)` bypasses Playwright's usual auto-scroll-into-view, so a graph that ended up further down the (now taller) column than before was silently being clicked off-screen.

Responsive breakpoints (`Studio.tsx`'s `layoutMode`): `desktop` (≥1024px, side dock), `tablet` (768–1024px, dock collapses to a tap-to-open icon strip overlay), `phone` (<768px, dock opens as a near-full-height slide-in sheet — `animate-slide-up-sheet` in `index.css` — with a drag-handle/close affordance, not a fixed-height strip). Tool rail is already icon-only/horizontal on phone via existing `lg:hidden` breakpoint classes; StudioToolbar serves as the top mini-bar on every breakpoint.

Fullscreen: native Fullscreen API on the Studio root, synced to `fullscreenchange` (not just button state, so Esc/browser UI stays in sync). Not bound to literal F11 — browsers intercept that key at the chrome level before JS reliably sees it — bound to `Ctrl/Cmd+Shift+F` instead. `Tab` hides all panels (menu bar, tool options, tool rail, dock, floating panels), guarded against firing while any input/textarea/contenteditable has focus.

Window menu items render real checkmarks (`Menu.tsx`'s `checked` field) reflecting actual panel/fullscreen/hidden state — not decorative. Window > "<Panel>" is a genuine on/off toggle (`showPanel` flips `PanelLayoutContext.setVisible`), not "always reveal, never hide" the way the old dock's tab-select was.

### Filter pipeline (`lib/filters.ts`, `filters/`)

**Image > Apply Filter is real, destructive, one-shot ImageData math** — a separate concern from the non-destructive Image > Adjustments *layers* (`lib/adjustments.ts`), even though both are reachable from the same `Image` menu and share a coding convention: `lib/filters.ts`'s functions are all `(params...) => (imageData: ImageData) => void` factories, matching `adjustments.ts`'s own shape exactly. Eight are real: Gaussian Blur (three box-blur passes at a third of the radius each — the standard cheap approximation, and the same idea `paint/selection.ts`'s feather comment already references), Box Blur (a true `O(width*height)` sliding-window separable blur regardless of radius, which matters at the large end of a 0–250px range), Motion Blur (directional multi-sample average), Unsharp Mask (blur-then-subtract, using Gaussian Blur internally), Add Noise (uniform or a sum-of-uniforms Gaussian approximation, mono or per-channel), Mosaic, Find Edges (Sobel magnitude over luminance, inverted to read as dark lines on light — the opposite of a raw magnitude map, matching Photoshop's own look; a *different* Sobel from `paint/magneticLasso.ts`'s selection-scoped cost field, same underlying math), and Emboss (a directional luminance derivative, offset to mid-grey). **Threshold and Posterize deliberately have no filter here** — they already exist correctly as non-destructive Image > Adjustments layers (see Per-page layer stack above); a redundant destructive version of identical math wasn't built. **Liquify opens the existing real brush-driven tool** (`paintEngine.ts`'s `liquify()`, already a selectable tool) instead of a dialog, per the spec's own allowance for reusing what's already there.

**`filters/FilterDialog.tsx` gives every filter a true live full-canvas preview** by mutating the active raster layer's real canvas on every param change — via `StudioCanvasHandle.getPaintCanvas` + `redrawLayer`, the exact mechanism a live brush stroke already previews with — rather than a separate small inset renderer. OK always re-runs the filter fresh against the snapshotted "before" pixels regardless of whether Preview happens to be checked at that moment (never "commit whatever's already on screen"); Cancel/Esc restores "before"; committing goes through `Studio.tsx`'s existing `handlePaintStrokeEnd(layerId, before)` — the same history-push-and-schedule-autosave path a paint stroke commit already uses, so a filter is undoable exactly like a brush stroke. `filters/filterDialogConfigs.ts` holds one `FilterConfig` per real filter (controls + a `run` function), keyed by the same id `menuDefinitions.ts`'s Apply Filter submenu already uses.

Two real bugs the unit tests (`lib/filters.test.ts`, pure ImageData math, no DOM — same convention as `adjustments.test.ts`) and a manual pass both caught:
- **`FilterDialog.tsx` was passing a plain `{data,width,height}` object to `ctx.putImageData()`.** `filters.ts`'s own functions deliberately only ever touch `.data`/`.width`/`.height` on their `imageData` argument — never a real DOM `ImageData` instance — specifically so they run in vitest's DOM-free environment (mirroring `adjustments.test.ts`'s own single-pixel fixture convention: `{ data: new Uint8ClampedArray(...), width, height } as ImageData`). But `ctx.putImageData()` is a real browser API with a strict `instanceof ImageData` check that rejects a same-shaped plain object outright — `FilterDialog.tsx` (browser-only code, never touched by a vitest run) needed a real `new ImageData(...)` specifically at its two `putImageData` call sites, while `filters.ts` itself stays exactly as vitest-safe as it was.
- **`embossFilter`'s directional sampling used a non-integer coordinate** (`x + cos(angle) * height`, where `height` and the trig functions are never whole numbers) **as a typed-array index.** A non-integer index on a typed array silently reads back `undefined` rather than an interpolated or rounded value, which propagates to `NaN` through the luminance math and then clamps to `0` on write — a flat, gradient-free image rendered as solid black instead of the correct mid-grey. Fixed by rounding inside the shared `clampCoord` helper (used by every filter's edge-clamped pixel lookup) rather than at each call site, so every caller benefits without individually remembering to round — caught by `embossFilter`'s own unit test, exactly the reason to write one.

## Text Editor (`src/components/textEditor/TextEditorPage.tsx`)

A standalone top-level page (`src/config/navTabs.ts`'s `'text-editor'` nav tab), **not** embedded in Studio — reached via the sidebar/bottom nav, matching the "own page, own switcher" requirement. TypeR itself is Studio-only; the editor connects to it one-way via a "Send to TypeR" pipeline (see below). **Known gap:** `'text-editor'` is currently absent from `navTabs.ts`'s `NAV_TABS` array (and explicitly filtered out of `BottomTabBar`), so there is presently no visible nav entry into this page in either the sidebar rail or the bottom tab bar despite the page itself being fully wired up — pre-existing, not touched by the work described below.

- **Multi-document tabs**: `TextEditorDoc[]` (`src/lib/textEditorStore.ts`), each with its own pages, persisted to IndexedDB (`text_editor_docs` key, separate from both Studio stores). Schema is versioned (`{ v: 2, docs }`, `loadTextEditorDocs` migrates the legacy bare-array v1 format via the same shape-detection `??`-default idiom `migrate.ts`'s `migrateChapter` uses) — see "Document library" below for what v2 added.
- **Pagination**: each doc's pages are A4-sized (`794×1123px`) `contentEditable` divs, each isolated behind its own `EditablePage` component wrapped in `React.memo` (`TextEditorPage.tsx`). This isolation is load-bearing, not cosmetic: a plain inline host div re-renders (and has `dangerouslySetInnerHTML` re-applied, destroying the live DOM and caret) on **every** parent re-render regardless of whether its own props actually changed — confirmed empirically by instrumenting a real browser session, and it's what made the autosave fix below insufficient on its own. `memo`'s bailout only works because every prop reaching `EditablePage` is kept stable: a per-page-index ref-callback cache, and `onInput`/`onClick`/`onKeyDown`/`onContextMenu` are each a `useCallback(() => {}, [])`-stabilized wrapper around a "latest logic" ref reassigned every render (so the exposed identity never changes, but the behavior it invokes is always current — the standard fix for "stable callback identity, non-stale closure"). `reflow()` does direct DOM manipulation on refs — pushes overflowing trailing block-children to the next page, pulls blocks back up from the next page to fill gaps — and only touches React state to change *page count* (splice the array, keep every untouched page's string reference identical, which is what lets `memo` skip re-rendering pages it didn't touch). Normal content edits never flow back through state at all; only autosave and explicit bulk actions (spell-check apply, find/replace, doc switch) do, and those intentionally force a full page re-render via `renderKey`.
- **Autosave**: `docsRef`/`activeDocIdRef` mirror `docs`/`activeDocId` state so live content can be read via `getDocsWithLiveContent()` (merges a fresh DOM capture into the active doc) without waiting for or forcing a re-render. The debounced autosave (`flushSave`) persists via this helper and updates `docsRef` directly — it deliberately **never** calls `setDocs` for the active page's own content, which is what used to force the `dangerouslySetInnerHTML` reset described above. Every doc-array mutation (`addDoc`/`closeDoc`/`switchDoc`/rename/duplicate/status-toggle) reads through the same live-content helper first, so switching or deleting a doc immediately after typing can't silently drop the untyped-back content. The mount effect guards against React StrictMode's dev-only double-invocation with the standard `cancelled` flag idiom — without it, when no doc exists yet, both invocations would independently create a fresh document (`genId()` gives each a different id) and whichever resolved last would silently replace the other's in-progress content. A `saveStatus` indicator (`saved`/`unsaved`/`saving`/`error`) sits in the tab bar; every save reads its own write back from IndexedDB and throws `"SAVE REGRESSION: saved content does not match source"` if the lengths disagree, a permanent regression guard against reintroducing the class of bug above.
- **Formatting**: `document.execCommand`-based toolbar (bold/italic/underline/headings/lists/align/insert-table) — the same pragmatic approach the reference prototype used; no custom rich-text model.
- **Tables** (`src/lib/textEditorTables.ts`, `TableToolbar.tsx`): a real `<table>` lives purely as HTML inside the page content, same as every other formatting concern here — no separate data model. Insert (rows×cols dialog), click-to-select (floating toolbar: add/delete row/column, delete table, plus a top-left "select whole table" handle), right-click context menu, Tab/Shift+Tab cell navigation (Tab from the last cell adds a row), Ctrl/Cmd+A + Delete/Backspace to remove a fully-selected table. All page-level handlers route through the same stable-ref-wrapper pattern `EditablePage`'s `memo` requires.

- **Keyboard shortcuts**: `useTextEditorShortcuts.ts` mirrors `useStudioShortcuts.ts`'s shape (one `window.addEventListener('keydown', ...)`), but inverted — a page (`.te-page`) *is* the text field this editor is built around, so shortcuts fire *while* a page has focus, not while it's blurred; only the Find/Replace bar's own `<input>`s suppress them (Escape excepted). `Ctrl+Enter` (hard page break) is deliberately **not** handled here even though it's a shortcut — each page's own `onKeyDown` (`handlePageKeyDown`) already owns it directly (it needs the specific page index), and handling it again at the window level would fire `insertHardBreak()` twice per keypress.
- **Pagination**: each doc's pages are A4-sized (`794×1123px`) `contentEditable` divs. `reflow()` does direct DOM manipulation on refs — pushes overflowing trailing block-children to the next page, pulls blocks back up from the next page to fill gaps — using `.firstChild`/`.lastChild` (not `.firstElementChild`/`.lastElementChild`): plain typed text with no wrapping block is a lone `Text` node with zero *element* children, which the element-only version could never push across a page boundary at all. State is only touched to change page *count* (splice the array, keep every untouched page's string reference identical) — **but that splice must rebuild from each page's live DOM content via `captureActiveDocPages()`, never from the possibly-stale React `pages` array**: React re-renders every page in the list on a count change (even ones whose own html string is unchanged in state), and that render is what actually commits whatever string sits in `pages[i]` back into the DOM via `dangerouslySetInnerHTML` — building the new array from stale state silently overwrites a live, unsaved edit (e.g. a just-inserted hard-break marker) with whatever old value was still sitting in memory. Normal content edits never flow back through state on every keystroke — only autosave (debounced 1000ms, captured fresh from refs, which also pushes a capped version snapshot — see Version history below) and explicit bulk actions (Spell Check button, Replace All, doc switch, version restore) do. **A real, critical bug found and fixed after the above was already written**: the page `<div>`s were still rendering `dangerouslySetInnerHTML` straight from `pages[i]`, so autosave's own flush — which legitimately *does* need to write the freshly-captured live content back into `docs` for persistence — flipped that prop from stale to live on every debounce tick, and React reset `node.innerHTML` on the exact node the user was actively typing into: the caret jumped, and under any timing overlap with continued typing, characters were silently dropped. Fixed by adding `pageSeedRef` (a `useRef<string[]>`, not state) as the *only* thing a page div's `dangerouslySetInnerHTML` ever reads from. Only genuine structural resets (doc load/switch/close/duplicate, Spell Check, Replace All, version restore, and the reflow page-count-change block above, which grows/shrinks `pageSeedRef` in lockstep without touching existing entries) write to it — `scheduleAutosave` and the unmount-flush effect explicitly never do, so a debounced save can no longer touch on-screen content at all. The unmount-flush effect was also closing over `docs`/`activeDocId` from mount time forever (`useEffect(() => () => {...}, [])`'s cleanup captured the very first render's values) — fixed by reading from always-current `docsRef`/`activeDocIdRef` mirrors instead.
- **Hard page breaks** (Ctrl+Enter, or Insert > Page Break): `insertHardBreak()` inserts an invisible `<div data-hard-break="true" data-break-id="...">` + a fresh empty paragraph at the caret. `reflow()` treats a hard-break marker as an unconditional forced split (regardless of overflow) — skipping a marker that's already a page's own first node (that one already correctly anchors *this* page; it's a *later* marker, e.g. two breaks typed back to back before either has its own page yet, that means split again) — and the page-count computation counts markers across *every* page, not just the last one, so a break on an otherwise-empty page still grows the page list. The marker is never stripped, so it keeps enforcing the same split on future passes even if surrounding content shrinks. **Focus-follow across the async page creation is the subtle part**: the target page doesn't exist as a DOM node until the next render, and — because that render also re-parses the *current* page's `dangerouslySetInnerHTML` (see above) — a plain JS object reference to the freshly-created paragraph goes stale (React's HTML re-parse creates a structurally-identical but distinct new node). The marker instead carries a one-off `data-break-id` attribute (a real HTML attribute, which survives the string round-trip), and the `pages.length`-keyed effect re-finds it live by that id once the real page exists, then focuses that page and places the caret — an object reference captured at insertion time would not have worked.
- **Cross-page arrow-key navigation and Backspace-merge**: `ArrowDown`/`ArrowRight` at the true end of a page's content (checked via `Range.compareBoundaryPoints`) moves the caret to the start of the next page; `ArrowUp`/`ArrowLeft` at the start does the mirror. Vertical nav lets the browser's own line-based movement run first (no `preventDefault`), then checks next frame whether the caret actually moved — if not, the browser had nowhere further to go and the page boundary takes over. `Backspace` with the caret collapsed at a (non-first) page's very start merges that page's children onto the end of the previous page and splices it out of the pages array outright (an explicit, discrete action — safe to `renderKey`-remount, unlike live typing), then re-focuses the merge seam once the remount's fresh DOM node exists. **`isCaretAtPageStart` treats a leading hard-break marker as invisible chrome, not real page content** — a page created by Ctrl+Enter has that break's own zero-height marker as its actual first child, one DOM level above where the focus-follow effect places the caret (at the start of the fresh paragraph *right after* the marker). Comparing the caret against the page's literal `(page, 0)` boundary point, as a first pass did, put the caret one position past "page start" in the exact terms the function checks for, so Backspace there silently fell through to the browser's own native contenteditable merge instead of the app's explicit one — different code paths that happened to often *look* the same to a user (the page still visually disappeared) but only converged by accident, and diverged outright whenever the native merge left the marker itself behind. The check now measures from just after a leading marker instead, matching `reflow()`'s own "a marker anchoring this page's start is chrome, not a split point" treatment. `mergeIntoPreviousPage` has the mirrored half of the same fix: it strips a leading hard-break marker before moving the rest of the page's children back, rather than carrying it along — otherwise `reflow()`'s own marker-forced page-count floor would see that same marker on its very next pass and immediately recreate the page the merge just removed, undoing the Backspace the user just pressed.
- **Page-number footers and zoom**: the "N / M" footer is a `<div>` rendered as a *sibling* of the contenteditable div (never a descendant), so it's automatically excluded from `captureActiveDocPages()`'s `innerHTML` read and never leaks into persistence/export — the same trick image resize handles use (below). Zoom (`transform: scale()`) is applied to an inner wrapper around the fixed-size page, with an *outer* wrapper explicitly sized to `PAGE_WIDTH/HEIGHT * zoom` so the page list still spaces/scrolls correctly (`transform` doesn't itself change layout box size).
- **Formatting**: `document.execCommand` first, direct DOM as a fallback where execCommand is unreliable (font-size uses the legacy-size-7-then-fix-up-the-`<font>`-tag workaround, since execCommand only supports sizes 1–7 natively, not arbitrary px; line-spacing has no execCommand equivalent at all and is applied directly to the selection's nearest block ancestor). Font family is a preset `<select>`; **font size is free-text** (1–999, Enter to apply, click-to-select-for-overtyping, up/down step buttons, silent revert to the last valid value on anything invalid) driving the same `applyFontSize()` workaround — not a preset dropdown, since the point size a user wants is unbounded. Text/highlight color (`<input type="color">`, no custom popover needed), bold/italic/underline/strikethrough, H1–H4, align (incl. justify), indent/outdent, undo/redo (native contenteditable undo stack — this codebase's own direct-DOM operations like reflow/table/image insertion aren't guaranteed to be tracked by it; a real custom undo history is out of scope). Custom fonts: a mount-time effect calls the same `loadStoredFonts()`/`registerStoredFont()` Studio's `FontsPanel` uses, since a user who never opens Studio this session wouldn't otherwise have them registered.
- **Live spell-check**: `src/lib/spellCheck.ts` — a small starter EN+AR misspelling dictionary (not a full language dictionary — there's no server to back a real one), flags exact-word matches (`findSpellIssues`) and multi-word idioms (`findPhraseIssues`, a literal substring scan for entries like `انشاء الله` → `إن شاء الله`; kept separate since the per-word regex only matches one contiguous letter-run) as clickable `.spell-miss` spans (`markMisspellings`/`markTextNode`). `findAllSpellIssues` combines both, letting a phrase match win over any single-word match it overlaps rather than double-flagging the same span with two different fixes. **Deliberately excludes a blanket `ان` → `إن` entry**: `ان` is a genuine, valid standalone word (the conditional "if") as well as a common typo, and this dictionary does zero-context exact-word matching — a blanket rule would silently "correct" a large fraction of valid usages. Runs live on an 800ms debounce (`markMisspellingsLive`, consolidated with the status bar's word/char-count recompute into one `scheduleContentAnalysis()` timer rather than two independently racing ones) directly on the live DOM — never through `captureActiveDocPages`/`commitActiveDocPages`/`renderKey`, which is only safe for the explicit "Spell Check" button's full re-mark — and skips whichever text node currently holds the caret, matching Word/Docs' own "don't flag the word being actively typed" behavior. `.spell-miss` styling (red wavy underline) lives in `src/index.css`, ported from the reference prototype's own CSS — it didn't exist anywhere in the shipping app before this pass, so spell marks were functionally real but visually invisible. Right-clicking a flagged word opens a "Change to / Ignore" menu — a small extension to the global `AppContextMenu` singleton (`ContextMenu.tsx`), which dispatches a `te-spell-fix` custom event on the target span (rather than calling back into `TextEditorPage` directly, since the singleton has no knowledge of which feature's text it's editing) that `TextEditorPage` listens for to trigger `scheduleAutosave()`. `stripSpellMarks()` always runs before export/send.
- **Find & Replace**: a real Find-only (Ctrl+F) vs Find & Replace (Ctrl+H) mode, match count, Previous/Next navigation, case-sensitivity and whole-word toggles. - **Tables**: Insert > Table opens a two-number-input picker (rows/columns); a visual hover-grid picker would be a nicer follow-up but isn't required. - **A generic "last real editing position" tracker, and a Range-API insertion path that doesn't depend on focus, were both needed for Insert > Table and Insert > Image** — two separate problems found only by testing, not by reasoning about it up front. First: reaching either action via the menu bar takes at least one click on a menu button, which moves focus away from the page *before* the action's own handler ever runs — reading `document.activeElement`/the live selection at call time only ever sees the menu button, never the page. `lastPageSelectionRef` fixes this by tracking the most recent real in-page selection continuously via a `selectionchange` listener (only when it's inside a `.te-page`), not just at one call site. Second — and the deeper one — both actions open a `swal()` dialog first (rows/columns; the file picker), and `execCommand`-based insertion afterward turned out to depend on the page actually holding focus at that moment, which SweetAlert2 doesn't relinquish cleanly: its own accessibility focus-trap stays attached for as long as its closing animation runs, empirically well over a second in this environment — not the ~200ms one might assume — well after the `swal()` promise itself has already resolved. `insertNodeAtLastPageSelection` sidesteps the question entirely by inserting `content` directly via `Range.insertNode()` on the saved range, which needs no element or document focus at all. It also syncs React's `pages` state to the live DOM immediately after inserting (`commitActiveDocPages(captureActiveDocPages())`) so `docs` (read for persistence/export) doesn't sit stale relative to the DOM until the next autosave tick — before `pageSeedRef` existed (see the pagination bullet above) this sync was load-bearing for a worse reason, since a later re-render could otherwise wipe the just-inserted content outright; now it's a freshness nicety, not a correctness requirement, since page content no longer renders from `pages[i]` at all.

  **Bridge** (`src/lib/typerBridge.ts`'s `applyTyperInsertMode(existing, incoming, mode, atLine?)`, a pure function with no DOM dependency): `TextEditorPage` calls `onSendToTyper(request)` → `App.tsx`'s `handleSendToTyper`, which does a **direct `studioProjectStore` read-modify-write** (`loadChapterStudioData` → `applyTyperInsertMode` → `saveChapterStudioData`) against the target chapter's persisted data, then navigates to open that chapter's Studio (`activeWorkspaceId`/`activeMangaId`/`activeVolumeId`/`activeChapterId` + nav tab, found by walking `workspaces` for the chapter's ancestry). This is deliberately **not** routed through Studio's own `pendingTyperScript` prop, even though that mechanism already existed pre-session for exactly this purpose — it turned out to be unreachable/unsafe for this flow: `TextEditorPage` and `Studio` render under mutually-exclusive nav tabs (`'text-editor'` vs `'library'`), so Studio is *always* unmounted while the dialog is usable, meaning a chapter opened via this flow always mounts Studio **fresh**. A fresh mount's own disk-reload effect (`loadChapterStudioData` on mount, setting `typerScript` from what it finds) resolves *after* a synchronous `pendingTyperScript`-consuming effect would have already applied the incoming text, silently clobbering it moments later — a real race, not a hypothetical one, and the reason the original single-string `pendingTyperScript` flow (`setPendingTyperScript(script); setActiveNavigationTab('library')`) never reliably worked either. Writing to disk *before* navigating sidesteps the race entirely: Studio's normal mount-time load just picks up the already-correct value. `Studio.tsx` itself needed **zero** changes for any of this.
- **Not implemented this pass**: comments, track changes, and the *optional* in-editor floating panels (Translation Preview and a live read-only page thumbnail) that SPEC describes as opt-in helpers while writing — real, separate scope beyond a working editor. No dedicated "switch Studio ↔ Editor" keyboard shortcut; switching is one click via the sidebar. A shortcut-*rebinding* UI (a settings surface to remap keys) was explicitly scoped out — `useTextEditorShortcuts.ts`'s bindings are fixed, matching `useStudioShortcuts.ts`'s own convention.

## Color system (`color/ColorPanel.tsx`)

RGB/Hex/HSV wheel + recent colors were already real; HSL and CMYK rows now use `colord` (+ its `cmyk` plugin, `extend([cmykPlugin])`) for the conversions rather than hand-rolled math — small, well-tested library, not bundled-heavy (a few KB, stays in the main chunk). **Saved palettes are real** — `src/lib/paletteStore.ts` (idb-keyval, `color_palettes` key, mirrors `fontsStore.ts`'s pattern) backs named `ColorPalette` lists in `ColorContext`; the panel's Palettes section lets you create/delete a palette and add/remove swatches (right-click a swatch to remove it). **Not implemented**: a dedicated multi-stop gradient editor UI (the Gradient *tool* itself is real and goes foreground→background, see Canvas engine above — there's just no UI for arbitrary custom gradient stops beyond that one pair).

## Fonts (`FontsPanel.tsx`, `src/lib/fontLoader.ts`, `src/lib/fontsStore.ts`)

Real font installation: upload TTF/OTF/WOFF/WOFF2 → `opentype.js` (dynamically imported) parses the embedded family name → registered via the `FontFace` API (`document.fonts.add`) → persisted to IndexedDB (`custom_fonts` key) and re-registered on every load. Installed families flow into `Studio.tsx`'s `allFontFamilies` (built-ins + custom) and are passed to both `TextPanel` and `TyperPanel` as a `fontFamilies` prop (defaults to the built-in list if omitted) — TypeR styles have always had a `fontFamily` field, and the style editor's Font select now actually drives it. **Google Fonts integration is intentionally not implemented** — SPEC lists it as optional, and pulling from Google's CDN would require network access, conflicting with this app's offline-capable design intent.

## Known gaps (honest, not silently dropped)

- **No Home/landing page.** Top nav is 5 flat tabs (Library/Text Editor/Settings/Teams/Cloud); Recent/Templates/Tutorials/Plugins/Account don't exist. Building nav destinations with no real content behind them would violate the no-placeholder rule — needs real features first.
- **Interactive control sizing** on mobile/tablet breakpoints hasn't had a systematic ≥44px touch-target pass — many buttons/sliders are still 24–32px (a few new additions, like the tablet dock icon strip, were sized to 44px; the sweep across every existing control wasn't done).
- **Smart objects** (layer *groups*, stack-aware adjustment layers, and layer *masks* all *are* implemented — see Per-page layer stack above) — declared as an intended feature (in tool lists, type unions, or SPEC) but not implemented. (Magnetic lasso, patch tool, slice tool, healing brush, and the full vector Pen Tool — anchors/handles, Path Selection, Direct Selection, convert-anchor-point, Stroke/Fill Path — *are* all implemented, see Canvas engine / Selection model / Vector paths above.) `toolGroups.ts`'s `curvature-pen` still shares an icon with plain `pen` — matches Photoshop's own flyout, which has no separate glyph for it either, so this is intentional, not a gap.
- (Selection feather/expand/contract/add-subtract/intersect, Transform Selection, Quick Mask, liquify's `reconstruct` mode, Crop, TypeR's Multi-Bubble mode, and brush symmetry *are* implemented — see Canvas engine / Selection model / TypeR above. The Layers panel navigating away on a plain click, and Color/Layers sharing a slot with other panels, *are* both fixed too — see Panel column above. A real multi-level Menu bar with submenus, a real stacked/reorderable Panel column, and real destructive Image > Apply Filter dialogs *are* all implemented too — see their own sections above.)
- **Menu/Image gaps**: New/Open Project, Open Recent, Save As, Preferences, Import > Original/Cleaned Pages/Translation File (page-image and translation-file import both stay PageManager/Translation-panel-only, not reachable from Studio's own menu), Guides, Safe Area, Snap to Grid/Guides, Image Size, Canvas Size, the three granular pixel locks (Transparent/Image/Position — only one coarse lock flag exists in the data model), AI bubble detection/auto-clean/AI Queue, and named multi-layout Save/Load (Reset Layout *is* real) are all permanently grayed — no backing subsystem exists, and building one wasn't in scope for the menu rewrite itself. Four Apply Filter submenu siblings (Smart Sharpen, Reduce Noise, Color Halftone, Glowing Edges) are grayed the same way — eight *other* filters in the same submenu tree are real (see Filter pipeline above).
- **Move tool only repositions (moves the Konva node of) text layers**, and for the same reason **canvas multi-select only covers text layers** (see Canvas selection above). Clean-patch (raster) and adjustment layers have no `x`/`y` offset in the data model and their Konva nodes aren't draggable — real Move-tool *layer* support for them would need per-layer offset fields plus a Group wrapper (and matching changes to export/flatten), a separate piece of work like layer groups/masks above. (The Move tool *does* already drag pixel **content** within an active selection on a clean-patch layer, by redrawing the layer's own canvas rather than moving a node — see Selection model above; that's a different mechanism and isn't blocked on this gap.)
- **Text warp** — needs path-based glyph rendering, which Konva's `Text` has no support for; it would mean generating glyph outlines (via `opentype.js`, already a dependency) and deforming them, rather than positioning text nodes. Not blocked on the run model — that now exists (see Text layers above), so kerning, baseline shift and per-character styling are implemented.
- **Vertical text mode (Japanese)** — not implemented; `layoutText()` only lays out horizontal lines. Per-line overrides' PSD export is a separate, smaller gap: `exportPsd.ts`'s `styleRuns` are per-character only, so `TextLayerData.lineOverrides` doesn't carry into PSD (PNG/JPG/WEBP does, via the shared `layoutText` path).
- **Type Region's auto-bubble-on-new-selection doesn't cover pen-path selections** (Make Selection from Path is a menu action with no natural gesture-completion moment) — those still become text containers via the click-inside-an-existing-selection path, just not the instant-on-completion one. A `mask`-kind selection (Magic Wand, Quick Mask output) has no clean vector form to persist as `TextLayerData.clipShape`, so Type Region falls back to a plain rectangular container at its bounds rather than a shape-clipped one; PSD export doesn't carry `clipShape` at all yet (see Text layers above). Type Region works with every selection kind this app actually has (`rect`/`ellipse`/`polygon`/`mask`, i.e. every real selection tool: both Marquees, Single Row/Column, all three Lassos, Magic Wand, and Pen-via-Make-Selection-from-Path) — concepts like a dedicated "rounded rectangle" selection, "AI selection", or "imported vector shapes" don't exist anywhere in this codebase's selection model and weren't invented for this.
- **TypeR's bold/italic overrides are still whole-layer.** The run model now makes per-character TypeR styling possible, but `parseTyperScript` only marks a *whole line* bold/italic, so nothing currently produces partial runs from a script — wiring that up is a separate change to the parser and its placement path.
- **Color**: no multi-stop gradient editor UI (saved palettes *are* implemented, see Color system above; gradient *text* is real but is a two-stop from→to ramp, same as the Gradient tool). **Fonts**: no Google Fonts (by design, offline-first; TypeR style font-family control *is* implemented, see Fonts above). **Music player, navigator/minimap, safe-area overlay** — not implemented (Grid and Rulers *are* implemented, see Canvas engine above).
- **Text editor**: no comments/track-changes, no in-editor floating Translation-Preview/page-thumbnail panels, no dedicated Studio↔Editor shortcut, and (pre-existing, unrelated to this pass) no visible nav entry into the page — `'text-editor'` is absent from `navTabs.ts`'s `NAV_TABS`. (Tables, images, a split-screen manga preview, a document library sidebar, and doc-level/section-level status tracking *are* all implemented — see the Text Editor section above.)
- **Text editor**: tables, images, and file attachments *are* implemented (see the Text Editor section above); no comments/track-changes, no in-editor floating Translation-Preview panel (the split-screen manga-page preview *is* implemented, see above, but it's not the SPEC-described Translation Preview), no dedicated Studio↔Editor keyboard shortcut (switching is one click via the sidebar).

## Conventions

- Keep the two IndexedDB stores (`workspaces_library` vs `studio_<chapterId>`) separate — don't fold raster/layer data into the main library object; that was a deliberate autosave-cost decision.
- New persisted shapes should include a `schemaVersion` field and a real migration path (see `migrate.ts` for the pattern), not just hope old data happens to still parse.
- Large/optional dependencies (`ag-psd`, `docx`, `opentype.js`) are dynamically imported (`await import(...)`), not top-level, to keep the main bundle lean — check `npm run build`'s chunk output after adding a new one; it should show up as its own chunk, not inflate the main one. Small libraries (`colord`, a few KB) are fine as regular top-level imports.
- `npm run lint` is actually `tsc --noEmit` (no separate linter configured) — run it after any change; `npm run build` is the stronger check since Vite/Rollup catch a few things `tsc --noEmit` alone doesn't.
- **Tests**: `npm test` is vitest over `src/**/*.test.ts` — pure logic only, no DOM. `npm run test:e2e` is Playwright (`e2e/`), driving the real app in Chromium; `vitest.config.ts` excludes `e2e/` or vitest would collect those specs and choke on Playwright's API. **e2e runs against a `vite build` + `vite preview`, never the dev server** — HMR would reload the page mid-test whenever a source file changed, producing failures that aren't real and blocking any work during a ~15-minute run. The build cost is worth it, and it means the suite tests what ships. Reach for e2e whenever the thing you changed only exists on the Konva canvas — **glyphs, strokes and layer compositing are not in the DOM**, so no DOM assertion can see them. `e2e/studioFixture.ts` has the helpers: `openStudio` (seeds a chapter into IndexedDB and clicks in) and `countDarkPixels` (a stage pixel probe).
- **Two traps the e2e pixel probe already fell into**, both of which made a test pass while proving nothing: (1) scope canvas queries to `.konvajs-content` — the Brushes panel draws its presets in black on their own canvases and swamps any global scan; (2) assert **deltas**, not absolutes — the stage carries a standing ~4.4k dark pixels from the page drop-shadow, so `> 0` is always true. If you write a regression test, verify it actually fails with the bug reintroduced before trusting it.
- The **whole app is gated behind `AuthGate`** (Supabase session) and `supabaseClient.ts` calls `createClient` at module scope — so a missing `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` throws on boot and renders a blank page, not just a broken Teams tab. `playwright.config.ts` injects dummy values and the fixture seeds a fake session into localStorage; for local dev you need a real `.env.local`.
- This session ported algorithms/behavior from two references: `src/assets/mangastudio (1).html` (a disconnected single-file prototype — TypeR parsing model, Tab-hide-panels, teReflow pagination) and the documentation in `src/assets/claude.md` (Arabic, describes that prototype's contracts). Both are read-only reference material, not part of the shipping app — don't wire them in or assume their code paths exist here.
